# agent-jobs v0.5.0 (2026-10-25)

Wave F, the brief-acceptance gate. Large work now goes from the owner's words to a merge only through an approved checklist and a release check that passed. The full list of changes is in [CHANGELOG.md](../../CHANGELOG.md).

## What Wave F gives you

- **A brief and a checklist in the project repo.** `brief/BRIEF.md` holds what the owner said, in the owner's own words. The text is frozen: anything said later goes under `## Additions`. `brief/CHECKLIST.md` splits the brief into numbered requirements R01..Rn. The orchestrator-only tools `checklist_init`, `checklist_get` and `checklist_set` write it, and only `checklist_set` writes the version, the approval and owner waivers.
- **Owner approval.** The read-only `briefing` job (`briefing_start`) prepares one or two short rounds of questions for the owner. The read-only `slicing` job (`slicing_start`) checks that every brief quote has a row and every row has a quote. Then the owner approves the checklist once. A manual edit of a hashed field cancels the approval.
- **Requirements in reports.** `job_start` takes `size` (`small` | `large`) and `covers:[R..]`. A job that names requirements reports on each of them in a `### Requirements` block.
- **`release_check` before merge.** The blind `judge` job (`judge_start`) gives a verdict on each live requirement for the code at a sha. `release_check(repo, sha)` (CLI `agent-jobs gate release-check`) checks the approved checklist, the judge's verdict and the feature jobs for that exact sha, and records a pass.
- **The merge-gate hook.** `agent-jobs hook merge-gate --agent A` is a `PreToolUse` hook on `Bash` in the orchestrator session. In a repository with an approved checklist it refuses `gh pr merge` unless the command carries `--match-head-commit <sha>` and `release_check` passed on exactly that head.
- **Also in this release:** job outcomes (`job_outcome`), auto-continue after a stop at the turn limit or the timeout, `PROGRESS.md` in every job dir, the daily cap on codex jobs, warnings about a stale MCP server, executor rules in the kind checklists, the brief reminder hook, and guard hardening. See the CHANGELOG.

## Upgrade notes

1. Rebuild and install the binary (README «Build and check»). Then run the daemon once. At start it runs `BackfillGateNames`, which stores the OWNER/REPO names of every repository with a stored approval. Until it has run, an approval recorded before names were stored stays unsure for a merge by name.
2. Register the new hooks in the orchestrator's Claude Code `settings.json` as README shows (the hooks block before «Brief reminder» and «Merge gate»): `UserPromptSubmit` runs `agent-jobs hook brief-reminder --agent A`, and `PreToolUse` with matcher `Bash` runs `agent-jobs hook merge-gate --agent A`. agent-jobs does not edit that file. Start a new session so that Claude Code loads the hooks and the MCP server reports 0.5.0.

## Known issues

- **The merge-gate reader refuses some harmless commands while a repository is gated.** Examples: the word `merge` in a `gh pr` title, label or body argument; a heredoc PR or commit body with extglob-like text such as `**(` or `C++(`; `gh -R "$R"`. Workaround: pass the body with `--body-file`, or write the title without the word. A fix is in progress.
- **Codex prompts that mention the word `merge` are refused while a repository is gated.** Workaround: pass the prompt from a file.
- **A Codex judge cannot see the job files.** Until this is fixed it counts as a warning, not a failure (owner decision 2026-10-25, [DECISIONS.md](../DECISIONS.md)). The fix is tracked separately.
