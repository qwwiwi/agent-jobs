# Architecture (stage 1 core + stage 2 MCP job tools + prune, doctor, system and file tools + shared-brain tools + cgroup containment + daily automation + schedules + dead-man's switch)

Implements [`docs/REFERENCE.md`](REFERENCE.md), section «How to do it yourself (minimum)», items 1–6. Quotes in Russian below are from the original, [`docs/REFERENCE.ru.md`](REFERENCE.ru.md) (section «Как сделать у себя (минимум)»). Deviations are only those in `docs/DEVIATIONS.md` (#6 model by kind × complexity, #7 naming are used here).

**MCP tools.** The reference starts jobs with the MCP tool `job_start` and reads reports with `job_result`. `agent-jobs mcp --role orchestrator|job --agent A` is that server (stdio, `github.com/modelcontextprotocol/go-sdk`), built on the same Manager as the CLI (`agent-jobs start/status/result/list/cancel`, kept for manual use).

Audiences live in `internal/mcp/registry.go`: `OrchestratorOnly` and `JobAllowed` (an allow-list: `memory_search`, `memory_write`, `notify_owner`, `check_mark`). A test fails when a tool is in neither list or in both. The job-role server registers only `JobAllowed` tools **and** a receiving middleware refuses any other `tools/call` and filters `tools/list`, so the boundary holds even if a hidden tool were registered. The job role does not open the job database.

## Components

| component | where | what it does |
|---|---|---|
| store | `internal/store` | SQLite tables `jobs`, `attempts`, `job_stats` (one summary row per job, rewritten at the end of each attempt, see Job stats), `daily` (one row: the last claimed day of the daily automation and its result), `intentions` (the agent's own goals), `schedules` (cron + prompt, stored job fields, the firing watermark and outcome), `checks`, `check_marks` and `check_alerts` (dead-man's switch: cron, grace, armed time, revision, the evaluation watermark; marks with time, note and job id, at most 20 per owner window, pruned once their expected time is judged; one alert row per missed expected time with its own delivery attempts), `owner_notifications` (every admitted `notify_owner` call: job id or NULL, text, urgency, created_at, delivered, error), `owner_pending` (one row per owner-waits job and attempt, key (job id, attempt): state `delivering`/`delivered`/`notify_off` (open) or `acknowledged`/`expired` (final), created_at; a table of the earlier one-row-per-job builds is rebuilt on Open, a replied row becoming acknowledged) and `hook_session` (one row: the orchestrator session the Stop hook holds), the last eight created on Open if missing (modernc.org/sqlite, WAL, busy_timeout). | brain | `internal/brain` | the shared brain (DEVIATIONS #2, #3). `Brain` interface; `Client` calls the brain's MCP servers over streamable HTTP (one short session per call: connect, one tool call, close; bounded by `timeout_seconds`); `Disabled` (no `brain` block) fails every call with `ErrNotConfigured`; `Fake` is the in-memory brain of the tests. `SocketClient` is the job role's brain: `memory_search` / `memory_write` as one JSON request per connection to `<state>/brain.sock`, everything else refused. ## State layout

`~/.agent-jobs/<agent>/` (override root with `AGENT_JOBS_HOME`):

- `jobs.db` – SQLite
- `config.json` – optional, see README
- `owner-rules.md` – owner rules (default path); the job profile when generated by `agent-jobs profile --from FILE...` (marked sections `<!-- agent-jobs:profile -->` … `<!-- /agent-jobs:profile -->` of the agent's own rules, ≤ 8 KB, a hand-written file replaced only with `--force`)
- `cards/<name>.md` – project cards (config `cards_dir`): front matter `repo:` (absolute top-level path) and/or `remote:` (identity `net:host/path` or `local:/abs/path`, see `RemoteIdentity`; control characters refused), then a body; the file is at most 4 KB, opened `openat(O_NOFOLLOW)` relative to the cards dir and read bounded from that descriptor (stack, check runner, do not touch, known traps). Read at prepare time; every card matching the job's repository (by path or by any remote) goes into the brief after the owner rules, ≤ 8 KB for the rendered section (headings included); an unreadable, unparsable or oversized card refuses the start of repository jobs. `agent-jobs card new --repo PATH` writes one from `cards/template.md`, `card list [--repo PATH]` shows them

`argv.txt`, `launches.txt` appear only in tests (the fake claude writes them). `<state>/tick.lock` is the per-agent lifecycle lock; `<state>/tmux.lock` serializes every tmux delivery (job-done lines, `notify_owner` from the daemon's proxy or the orchestrator's process), so two lines never interleave their keystrokes; it is polled (`LOCK_NB`) only until the delivery's 10 s deadline. A job-done line that times out ends that tick's delivery pass (the rest stay pending for the next tick), so a hung tmux never holds the tick. A line ending in `;` is sent with one trailing space: tmux takes an argument ending in `;` as a command separator, and a backslash before it is not a reliable escape. `<state>/brain.sock` is the daemon's job proxy (memory calls when a brain is configured, `notify_owner` always).

## Flows

**Start.** `agent-jobs start` validates kind, limits (defaults 80 turns / $10 / 45 min; above 200 / $50 / 180 → error, never clamped), resolves repo + base to a commit SHA, picks the model (explicit `--model`, validated as a model name so it can never become a flag; else the kind × complexity table; neither given = rejected, complexity is never defaulted), inserts a `queued` row and prints the id. Nothing runs yet.

**Tick** (every minute, also `agent-jobs tick`) runs under an exclusive `flock` on `<state>/tick.lock` (also taken by `cancel`), so two daemons or a manual tick never interleave. In this order:
1. *Collect* each `running` job. A claimed job without a recorded pid (daemon died between spawn and pid write) is adopted from `wrapper.json` if its token matches; with no `wrapper.json` after 1 minute it is `failed` under `admit.lock` ("the wrapper never registered", work dir kept). Then: `exit_code` present → stream.jsonl is read *after* it (so the result is complete) → verdict; else past `started_at + timeout` → SIGTERM to the process group, 10 s, SIGKILL → `timeout`; else wrapper PID dead → re-check exit_code, then `failed` ("wrapper died without writing exit_code").
2. *Launch* queued jobs while fewer than 2 are running. Launch = claim (`running` + token) → prepare job dir (owner rules must be readable and ≤ 8 KB, else the job is `failed` with "refused to start: …") → decide the containment (Linux: probe a throwaway `systemd-run --user --scope`; see «Cgroup containment») and record the scope unit on the row → start `agent-jobs run-wrapper <jobdir> --token T -- claude <args>` with `Setsid` (own session → own process group, not a child of the daemon's group), through `systemd-run --user --scope --quiet --collect --unit=agent-jobs-<agent>-<id>.scope --property=TimeoutStopSec=<kill grace> --` when there is a scope (systemd-run execs the wrapper inside the new scope, same pid) → store PID = PGID.
3. *Notify* finished, not yet notified jobs: `tmux send-keys -t <target> -l "<line>"`, then `tmux send-keys -t <target> Enter` (both with `-L <tmux_socket>` when configured). The line is printable-only (whitespace → space, control/format characters such as Ctrl-U, ESC, bidi overrides dropped; title capped at 120 runes), so a title cannot type keystrokes into the session. With a target configured, a job is marked notified only after tmux accepted the line: a failing tmux (missing session) keeps it pending, logged and retried next tick, and cleanup waits. With no target configured notify is off: the line goes to the daemon log and the job is marked notified at once, so the 30-minute cleanup still runs.
4. *Cleanup* jobs notified ≥ 30 min ago (see below).

**Idle after result.** `claude -p` can stay alive after its final `result` event (seen with background subagents: every result was printed, then the process idled with only the job's MCP server as a child) and would otherwise run into the timeout. While claude runs, the wrapper follows stream.jsonl. When the last event is a `result`, the last `background_tasks_changed` event lists no task, and for the whole grace period (`idle_after_result_seconds`, default 180) nothing new arrived and claude had no live descendant other than the job MCP server (this binary running `mcp --role job`, from `/proc`; a live child restarts the grace), the wrapper sends claude SIGTERM, then SIGKILL after 10 s (as cancel does). It then settles report.md, in this order: the last `result` text if it starts with `## Summary`; else a report.md the job wrote itself, left untouched; else the last top-level assistant text (no `parent_tool_use_id`, so no subagent output) that starts with `## Summary`; else a short note that the job ended without a report, writes `closed_idle_after_result` and sets exit_code by the last result: 0 when its subtype is `success`, not an error, and a report was found; 1 otherwise. The session sweep and the rest of the wrapper run as after a normal exit. The verdict records «closed by the idle-after-result rule (…)» in the job row; turns and cost come from the last `result` event. `idle_after_result_seconds: -1` turns the rule off. Linux only; elsewhere the rule is off.

**Verdict.** exit_code ≠ 0 → failed; stream `result.is_error` (e.g. max turns / budget) → failed; exit 0 but empty/missing report.md → failed ("exit 0 without a report"); a job with an acceptance command whose command did not pass → failed (below); otherwise succeeded. Turns and cost come from the stream `result` event; duration is wall time from start to collection.

**Brief checklist** (Wave F, F1/F2; `internal/checklist`, `internal/mcp/tools_checklist.go`). *Format.* `Parse` reads the header (`id`, `brief` = `brief/BRIEF.md`, `version` ≥ 1, `approved: no` or `<RFC 3339> owner sha256:<64 hex>`; a malformed approved line voids the approval instead of failing the parse) and one table `| ID | Brief quote | Contract | Rationale |`; text outside it is ignored and not hashed. Each row is normalized (`NormalizeRow`: white space collapsed, `\\` and `\|` unescaped; ID `R<nn>`, `R<nn>i`, `G<nn>`, `D<nn>`, an `A` ID refused; contract one of live/deferred/dropped plus optional `placeholder-ok`; a deferred or dropped row needs a Rationale). `Hash` = sha256 over `ID|verbatim|contract|placeholder-ok|rationale\n` per row in file order (a `\` and a `|` inside a field escaped as `\\` and `\|`, so a literal `\|` hashes apart from `|`) and `BRIEF.md|<sha256 of BRIEF.md>\n`. *Approval.* The hash is unkeyed (anyone editing the file can recompute it), so the approved line is informational. `checklist_set approve` (needs `approve_quote`) stores a `checklist.Record` in the store table `checklist_approvals` (main worktree, checklist id, version, checklist hash, `BriefPrefixSHA256` = sha256 of the BRIEF text above `## Additions` with trailing white space trimmed, time, the redacted quote; a log, the highest `seq` of a repository is in force) after the files are written (a failure in between leaves the content unapproved). `Status(brief, rec)` is approved only when `rec`, the repository's latest stored approval, names the current hash, version and id; an approved line `rec` does not back is void. `checklist_init` stores a `ChecklistInit` (repository, id, `BriefPrefixSHA256`) after writing the files (removing them again when that fails) and refuses an id with a binding: `Store.Binding(repo, id)` = the BRIEF prefix hash of the id's latest approval, else of its init, nil when the store has neither (a new brief takes a new id). `BriefPrefix` ends at `additionsAt`: the first `## Additions` line outside a ``` fence (a heading inside a fence never counts; no fallback). The prefix is balanced by construction: `Init` refuses owner words with an unclosed fence (`fenceOpen`: an odd number of lines starting with ```; `ErrUnclosedFence`, which says to close it) before the literal-heading check, `Apply` refuses a bound call whose BRIEF prefix leaves a fence open (a hand-written file) before the prefix comparison, and `AppendAdditions` closes a fence a quote leaves open, so the heading it writes is never inside a fence. *One managing agent per repository.* Records live in the store of the agent that wrote them: `Apply` takes `bindingOf(id)`; without a binding for the file's id a call with no rows, additions or approve returns the status and writes nothing (another agent's approved line is never voided), any other is refused (`ErrOtherStore` when the file has an approved line). *Writes.* `Apply` redacts every raw input (row fields, addition quotes, the CHECKLIST text as read) with the real redactor before anything is normalized (a PEM block or fragment is only recognized with its line breaks), refuses when the BRIEF prefix differs from the id's binding, reads both files, appends additions under `## Additions` (`### <date>` and the quote; the heading added once), redacts the whole BRIEF and every row field, recomputes the hash (refused when the redacted BRIEF's prefix no longer matches the binding: a redactor rewriting the owner's words); the version goes up when the hash changes or a void approval line is found (a manual edit, a forged line), which drops the line; while the stored approval holds, the line is rewritten from it; `approve` sets one over the result (`Result.Record`, stored by the tool); a new `G` row without an addition in the same call is refused; `expect_version` refuses a stale call. `WriteBoth` writes synced temp files in `brief/`, renames BRIEF then CHECKLIST, and puts BRIEF back when the second rename fails. Waivers are validated (approved after the call, a live requirement, a full commit id that exists) before any file is written and stored after, bound to the approved hash and version; `checklist_get` lists them only while approved and parses the file redacted. A `checklist_waivers` table from before the version joined its primary key is rebuilt once at `Open` (`migrateWaiversKey`: one IMMEDIATE transaction, rows copied with their version, 0 for older rows). *Two renames.* `WriteBoth` is two renames, not one atomic step: a crash between them leaves the new BRIEF next to the old CHECKLIST. That fails closed: the hash then differs from the stored approval's, so the checklist reads as not approved until `checklist_set` runs again (and an edited BRIEF prefix is refused). The lock keeps every other checklist tool, of any agent, from reading the half-written pair.

**Acceptance command** (Wave D; `internal/jobs/acceptance.go`). Opt-in: config `acceptance_allowed` (default false); without it `job_start`, `schedule_add` and `agent-jobs start` refuse a command. At launch the daemon requires both its active permission and the current disk opt-in; enabling requires a daemon restart. The wrapper receives that authorization as `--acceptance-allowed` (absent means denied) and checks `config.json` again before running the command, so a later revocation or invalid edit fails closed (the job then fails «acceptance did not run»). `job_start` / `schedule_add` field `acceptance_cmd`, `agent-jobs start --acceptance-cmd`: one line (no newline, CR or NUL anywhere in the input, checked before trimming, so a trailing or leading one is refused too), valid UTF-8, at most 1 KB, trimmed, stored in `jobs.acceptance_cmd` (a job schedule stores it in `schedules.acceptance_cmd` and passes it to the jobs it fires); refused for `review` and `research` jobs (they change no code). The wrapper, not the daemon, runs it: after claude (or codex) exited 0, report.md is there and the session sweep was complete, so it runs in the job's own containment (the same scope or session) without any extra spawn path. It reads the command from the job row and records the start together with the daemon's deadline for it (`acceptance_started_at`, `acceptance_deadline` = start + the acceptance timeout the wrapper applies + 2 min) in one conditional update that fails once the daemon claimed the job's timeout (below), then runs `/bin/sh -c <cmd>` in `<jobdir>/work` in a process group of its own, recorded as `acceptance_pgid`, stdin `/dev/null`, with a scrubbed environment (only `PATH USER LOGNAME SHELL LANG LC_* TZ TERM` of the wrapper's; `HOME` a fresh `<jobdir>/acceptance-home`, `TMPDIR` its `tmp/`, so nothing finds the agent's dotfiles, credentials or state dir through them; then the job's git environment and the job marker `AGENT_JOBS_JOB`, so it starts no nested job and `doctor procs` finds what it leaves), and **without the guard**. Timeout `acceptance_timeout_minutes` (default 15, at most 60): SIGTERM to the group, SIGKILL after 5 s, result `-1`. While the command runs the wrapper catches SIGTERM, SIGINT and SIGHUP: it ends the command's group the same way and exits 143 without a result or `exit_code`. The daemon's `killJob` (timeout, cancel, stop) also ends the recorded acceptance group after the scope or wrapper group, re-reading the row: while the group's leader is alive and leads it, the whole group is signalled only if the leader carries the job's marker; once the leader is gone (the shell died on SIGTERM while a child that ignores it holds its stdout open, and the daemon's `KillGrace`, shorter than the wrapper's 5 s, killed the wrapper first), the surviving members of the recorded group are found in `/proc` and ended only if every one of them carries the job's marker (a member without it means the pgid is not, or no longer, the job's, and nothing is signalled), each through a pidfd opened before its group and marker are re-checked, SIGTERM, `KillGrace`, SIGKILL. stdout and stderr go to `acceptance.log` (the last 64 KB, a note says how much was cut; a line cut by that cap is dropped whole, so a value split by the cut leaves no part of itself; the file stays raw like `stderr.log`, every read of it is redacted). Then the session is swept again (an incomplete sweep writes the sweep marker and fails the job as usual), and only then the exit code and duration are written to the row (`acceptance_exit`, `acceptance_duration_sec`, `acceptance_pgid` back to 0), before `exit_code`. The daemon re-reads the row when it judges a succeeded run: no recorded result → failed «acceptance did not run», `-1` → «acceptance failed (timeout after Ns)», non-zero → «acceptance failed (exit N)»; the job-done line then ends `· acceptance failed (exit N)` (or `(timeout)`, or `· acceptance did not run` / `· acceptance result unreadable` when no result was recorded), the HTTP API error code is `acceptance_failed`, `job_result` returns `acceptance {cmd, ran, exit, timed_out, duration_sec, log_tail}` (the last 16 KB of the log, opened like `report.md`: `openat` through the state dir with `O_NOFOLLOW` at every level, only a regular file of the agent user with one link, so a hard link or a symlinked job dir is refused) and lists `acceptance.log`; `agent-jobs status <id>` prints an `accept:` line. Timeout race: the daemon's deadline for a job is `started_at` + its timeout, or the later recorded `acceptance_deadline` (never its own config, so changing `acceptance_timeout_minutes` while the daemon runs cannot cut a run short); the row it judges by may predate the acceptance start, so it only preselects, and the decision is `ClaimTimeout`, one conditional update that sets `timed_out_at` only if the row, as it is then, is past both deadlines. SQLite serializes it with the wrapper's start: either the start is recorded first and the claim fails (judged again next tick), or the claim wins and the start fails (the command never runs). A resume resets the acceptance fields and `timed_out_at` (`Requeue`), archives `acceptance.log` with the attempt, and the resumed run is accepted again. Not a security boundary: the command runs the code the job wrote, as the agent user, without the guard or a file-system sandbox, so a job can change the test it is checked with; it catches honest mistakes, not a hostile job.

**Secret redaction** (`internal/jobs/redact.go`). `Redact` runs a fixed list of RE2 rules in order (specific formats first, the generic key=value last, so a value already replaced is not matched again: values never contain `[`): PEM private key blocks (any `-----BEGIN … PRIVATE KEY-----` label: PKCS#1/#8, EC, OPENSSH, ENCRYPTED, and `PGP PRIVATE KEY BLOCK`; also one cut off before its END line), `sk-ant-…`, `sk-…`/`sk-proj-…` at a word start, `gh[pousr]_…`, `github_pat_…`, `xox?-…`, `AKIA`/`ASIA` key ids, the value of `aws_secret_access_key`, `AIza…`, Telegram bot tokens (`<8-10 digits>:<35+>` after a non-token character, the start, or `bot` as in the Bot API URL `/bot<token>/getMe`; nothing after the token is consumed, so two tokens one separator apart are both found), JWTs (`eyJ….….…`), the token after `Bearer`, and the value (16+ characters, no quotes, spaces, brackets or separators) after a key containing `token`, `secret`, `password`, `passwd` or `api[_-]key` followed by `=` or `:`. Every variable-length value is matched whole (no upper bound; RE2 stays linear), so a long credential is never replaced only in part. Each match (or its secret group) becomes `[redacted:<kind>]`; the result is idempotent. Oversized policy: input past `MaxRedactBytes` (4 MiB) is not scanned; it is cut right after the last line break before the cap, however far back (with none, nothing of it is kept), so the incomplete line at the cap goes whole and no value is split into a too-short scanned prefix; everything after the cut is replaced by `[redacted:unscanned N bytes past the 4194304-byte scan cap]`. **PEM blocks** are not a pattern over the whole text but a line scanner (`redactPEM`, one linear pass, run first by `Redact` and so on every redaction and read, cut or not): dropping the partial line at a cut may take a key block's BEGIN or END line with it (now or in a log or report cut by an earlier build), and what is left matches no pattern. A marker is a line of its own, `-----BEGIN|END … PRIVATE KEY( BLOCK)?-----` with indentation, trailing blanks and a CR ignored, and around it only what files and listings put there (a diff or quote prefix `+ - > # |`, an assignment `KEY=` / `key: `, quotes, an escaped `\n`, a trailing comma); a marker quoted inside prose is none, so a report that talks about key blocks keeps its text (a whole block written on one line, as with escaped line breaks in JSON, and a BEGIN marker followed by an escaped `\n`, through the end of that line, are rules of their own). Key body lines are base64 (also with one diff/quote prefix character or a trailing quote or comma), armor headers (`Proc-Type: 4,ENCRYPTED`, `DEK-Info: …,…`, `Version:`, `Comment:`) and blank lines. Redacted: a block from BEGIN through END; a BEGIN with no END after it through the end of the text; an END with no BEGIN before it together with the contiguous run of body lines above it (from the start of the text when the run reaches it; a base64 line shorter than a full key line ends the run unless it is right above the END line, so a word like `ok` above a key body stays); a markerless run of at least two base64 lines of 40–80 characters at the text's start or end or next to a cut note (`[... N earlier bytes cut …]`, `[redacted:unscanned …]`), the middle of a key both of whose markers fell outside a window. Each becomes `[redacted:private-key]`. The acceptance log write cap (`tailBuffer`) also follows the markers of the output it evicts (`pemTracker`, at most 256 bytes of a line kept): when the evicted part opened a block that is still open, the kept tail is redacted from its start until the END line (or to its end). **Redact before cut**: job-derived text that is shortened (`RedactPrintable`: the finish, stop and cancel messages with a scope error, the stop reason, the previous attempt's error in a resume brief, process command lines in sweep notes, `doctor procs` and the resume refusal, the codex `turn.failed` message and stream error, the sweep and idle-close markers, the title on the job-done line) is redacted first, then made printable and redacted again (dropped control characters may join a value), then cut, so a value cut short never escapes its rule. Where it applies: when a job reaches a terminal or stopped status (`Manager.settled`, under the lifecycle lock, after the scope stop and the sweep, so no process of the job is left), `report.md` is opened `O_NOFOLLOW|O_NONBLOCK`, redacted only when it is a regular file, and at most 4 MiB + 1 byte of it is read (`io.LimitReader`; an oversized report's rest is never read, its size comes from `fstat`). The redacted text is written to a unique `os.CreateTemp` file in the job dir (0600, `O_EXCL`), fsynced, renamed over `report.md`, and the dir fsynced; with `keep_raw_reports` the whole original is first streamed the same way into `report.raw.md` (0600). **redaction_pending**: `Store.Claim` sets the job column `redaction_pending` (an attempt may write `report.md` from then on), and `Store.Finish` sets it again in the same update that makes the row terminal, so the mark is persisted before any redaction is tried; the migration that adds the column marks every existing job (queued and running ones write their report later; finished ones were settled by a build that did not redact or may have died before the rewrite; redaction is idempotent and a job without a regular `report.md` is just cleared). It is cleared only after the report of the ended attempt was redacted (or there is no regular `report.md`), and only while the row is not queued or running. A failed rewrite or a daemon that died between `Store.Finish` and the rewrite leaves it set, and every tick (`retryRedactions`, also the daemon's first tick after start) retries those jobs until it succeeds. Readers never rely on it: `job_result`, `agent-jobs result` and the HTTP API's `?report=1` always redact on the fly (`RedactRead`: a report cut at the read cap first loses its whole incomplete last line, all of the text when it has no line break), and the log archive copies `report.md` and `report.attempt-<n>.md` redacted on the fly (`archiveReport`, the same bounded reader and cut as in place), so an archived report is never unredacted even while its in-place redaction is pending. The daemon log redacts job-derived text: the finish and stop lines (status message), the launch refusal, the sweep note (process command lines), scope/adopt errors, notify and cleanup errors. On read: `DoneLine` (so the tmux line and the daemon log), `job_result` (report, error), `agent-jobs result` (the same bounded reader as `job_result`: `openat` with `O_NOFOLLOW|O_NONBLOCK`, regular file of this user with one link, at most 4 MiB), `/v1/jobs/{id}?report=1`, the stats row (`result_subtype`, tool/skill/rule names) and the previous attempt's report or last messages in a fresh-session resume brief. `job_result`'s acceptance `log_tail` is redacted the same way (`ReadAcceptanceLogTail`: at most `acceptanceReadCap` bytes read, a line cut by the read dropped whole, redacted before the cut to the tail size, the tail's incomplete first line dropped), and so is the acceptance note on the job-done line (redacted before it is cut, then `RedactPrintable`). Not redacted: `stream.jsonl`, `stderr.log`, `acceptance.log` on disk (kept raw in the job folder and gzipped raw into the archive) and `prompt.md`.

**Brief size** (`internal/jobs/briefsize.go`). `newJob` (job_start, `agent-jobs start`, schedules with a kind) refuses a brief above `max_brief_bytes` (default 32768) with an error that names the key and suggests splitting. `BriefSizeWarning` measures the brief: files named = distinct path-like tokens with an extension (`a/b.go`, `PLAN.md`, `x.go:12` counts as `x.go`, single-character stems included; URLs and abbreviations `e.g`, `i.e`, `a.k.a`, `a.m`, `p.m` do not), headings = lines starting with `## `; above `brief_warn_files` (default 40) or `brief_warn_headings` (default 8) the job is still queued and `job_start` returns `size_warning` (`agent-jobs start` prints it on stderr).

**Progress section** (`prompts/report-contract.md`, `internal/jobs/report.go`). The contract asks for `## Progress` after «Not done / uncertain»: one line per step, `- HH:MM UTC <step>`. `ReportSection` finds a `## ` section by name (case-insensitive, headings inside ``` fences ignored, the last one wins); `job_result` returns `not_done` and `progress` (empty when missing, never an error); `ReadFirst` reorders the report for `agent-jobs result`: «Not done / uncertain», then «Progress», then the other sections in their order.

**Daemon restart.** The wrapper lives in its own session (and, on Linux with systemd, in its own scope under the user manager's `app.slice`, outside the daemon's service cgroup) and writes `exit_code` itself; the daemon keeps no in-memory state. Killing the daemon (even SIGKILL) leaves the job running; the next daemon/tick finds `exit_code` and collects it (tested with the real binary).

**Cancel** (under the lifecycle lock and the job's `admit.lock`). `queued` → `cancelled`; `running` → stop the job's scope, or without one TERM group / 10 s / KILL → `cancelled`; `stopped` → `cancelled` (turns/cost of the stop kept; notify and cleanup then run as for any finished job). Other terminal jobs cannot be cancelled.

**States** (Wave E2, DEVIATIONS #15):

```
queued    ──tick claims──────────►  running      (attempt + 1)
queued    ──job_amend────────────►  queued       (attempt 0: brief += update; a queued resume: update += text; position kept)
queued    ──job_stop─────────────►  stopped      (attempt 0: no session yet; a queued resume keeps its update)
queued    ──job_cancel───────────►  cancelled
running   ──exit_code + verdict──►  succeeded | failed
running   ──past timeout─────────►  timeout
running   ──job_stop─────────────►  stopped      (work dir + session kept, not notified, not cleaned)
running   ──job_cancel───────────►  cancelled
stopped   ──job_resume───────────►  queued       (next attempt of the same id)
timeout   ──job_resume───────────►  queued       (next attempt of the same id)
failed    ──job_resume───────────►  queued       (next attempt of the same id)
stopped   ──job_cancel───────────►  cancelled    (then notified and cleaned up)
succeeded, cancelled: final
```

**Stop** (`job_stop` / `agent-jobs stop`, under the lifecycle lock and `admit.lock`). `queued` → `stopped` (attempt 0, no session yet). `running` → the job's scope is stopped (or, without one, its process group killed) exactly as for cancel; a scope stop that fails is recorded as pending, named in the error field and retried every tick, and the job cannot be resumed until it succeeds; the turns come from the number of distinct assistant messages in `stream.jsonl`, and a `result` line there is ignored (the job can write the stream), so the cost is unknown (said in the error field) unless the wrapper wrote `exit_code` first; the same holds for a timeout and a dead wrapper. The row ends `stopped` with the reason, and the attempt's cost is marked unknown (`cost_unknown`: a resume counts it at its whole budget). Then, the row no longer running, the job's processes that left its process group are swept as `doctor procs --kill` does for this job only (marker or the job's session): killed, or, when one leads its own session (`setsid`, may host other work), left running and named in the error field, as is "not checked" without Linux `/proc`; cancel, a timeout and a failure do the same. Then the digest of the session transcript is recorded (as at every attempt's end, always after the sweep). A job whose `exit_code` already exists is collected with its real verdict instead (the stop is refused). A stopped job is not notified and not cleaned up (PendingNotify / PendingCleanup skip it; prune skips it): its worktree, uncommitted files and session stay until it is resumed or cancelled.

**Resume** (`job_resume` / `agent-jobs resume`, under the lifecycle lock). Only `stopped`, `timeout` and `failed`; a job that never prepared its folder (refused to start) is refused, and so is one whose records prune already moved into the log archive (an archive dir exists for it; `stopped` jobs are never archived). The same job id runs its next attempt: `Store.Requeue` archives the current attempt into the `attempts` table (number, mode, status, model, limits, usage, error, context, session id, times), resets the run fields (pid, token, finished/notified/cleaned, usage, error) and queues the row again with the new limits and the update (`pending_context`); `created_at` is kept, so the job keeps its original queue position. Limits: each one given explicitly or what the previous attempt left of its own (turns − used, budget − cost, minutes − elapsed); an attempt that ended without a `result` event (killed, stopped) has an unknown cost and counts at its whole budget, so the default budget is then nothing and `max_budget_usd` must be given. All attempts together stay within the ceilings: the new limit plus what earlier attempts used (unknown costs at their budgets) must fit, never clamped; nothing left and nothing given is an error. A job stopped while queued (attempt 0) gets the update appended to its brief and starts as a first attempt; a resume stopped while still queued (never ran, not archived again) keeps its update and gets the new one appended. A resume whose launch was refused or interrupted (it never ran claude) also keeps its update, and the fallback's «Previous attempt» skips such attempts. Refused, here and again at launch: a live process of the job outside its process group (one with its marker, or left in its last wrapper's session; the sweep never kills a session leader); a `.claude`, `CLAUDE.md` or `CLAUDE.local.md` in the job dir, any of them anywhere in `work/` of a job without a repository, or any of them (`**/.claude`, `**/CLAUDE.md`, `**/CLAUDE.local.md`) that differs from the base commit (changed, staged, untracked or ignored files): claude loads settings, local settings, hooks, skills, agents and instructions from them, outside the guard, and the job (or another job) could have written them. `settings.json` also pins `disableAllHooks: false` (`--settings` outranks project settings). Same id, not a new linked job: claude finds a session by the cwd's project directory, so the attempt must run in the same `<jobdir>/work`, which belongs to the job id. On launch (`Claim` counts `attempt`), `prepareResume`: moves the previous run files to `attempts/<n>/` and its report to `report.attempt-<n>.md` (prune keeps small top-level text files), rewrites `settings.json`, `mcp.json`, `gitconfig`, `no-hooks/` from the config (the job dir is writable by the job; a filled `no-hooks/` refuses), restores the worktree if cleanup removed it (`git worktree add` at `refs/agent-jobs/jobs/<id>`, then `staged.patch` with `git apply --cached`, `uncommitted.patch` with `git apply`, `untracked.tar` extracted without `..`, absolute names or writes through symlinks; the owner mark re-written) and verifies it as cleanup does, then writes `resume.md` (the update: «Orchestrator update», the context, «Continue the task with this update; keep the report contract», the attempt's limits) and `fallback.md` (the prompt rebuilt from the database brief, owner rules and cards, plus «Previous attempt»: status, turns, error, its report or else its last assistant text, where its commits are, plus the update and «say so in Not done / uncertain»). If the session transcript is in the job's own project dir (`projects/<work dir, non-alphanumerics → '-'>/`; a long name is matched by its first 200 characters) and still has the SHA-256 recorded when the previous attempt ended (transcript plus its `<id>/` directory; another job can write `~/.claude/projects`), the wrapper runs `claude … --resume <session id>` with `resume.md` on stdin and `--fallback-prompt fallback.md --fallback-session <new id>`; if not (missing, or changed since), a fresh session (`--session-id <new id>`, stdin `fallback.md`, run mode `fallback`). The wrapper falls back by itself when a resume exits non-zero (not by a signal) before any `assistant` or `result` event: the failed stream is kept as `stream-resume-failed.jsonl`, `fallback_session` records the new id (the daemon validates it and stores it on the row when it collects), and claude runs once more in the fresh session. The job-done line of attempt N > 1 ends `· resumed (attempt N)` (`, fresh session` in fallback mode); `job_result` lists all attempts. The subagent cap stays per job (the counter is monotonic across attempts).

**Amend** (`job_amend` / `agent-jobs amend`, under the lifecycle lock): a queued first attempt gets `UPDATE … SET brief = brief || <update> WHERE status='queued'`; a queued resume (attempt > 0) gets the text appended to `pending_context`, which is what the resumed session (and a fallback) receives. The row's `created_at`/rowid, so its queue position, are unchanged. Any other status is refused.

**Sessions on disk.** Without `--no-session-persistence` claude keeps each job's transcript in `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<cwd with every non-alphanumeric character replaced by '-'>/<session id>.jsonl` plus a `<session id>/` directory (tool results, subagent transcripts); typically tens of KB to a few MB per job. `SessionPaths` finds them by the job's session id (glob over `projects/*/`, the id is a UUID the daemon generated), and `prune` removes them for the jobs it prunes (every attempt's session), never anything else in the claude config dir.

**Scope stops** (timeout, cancel, and every time a scoped job's row turns terminal). `systemctl --user stop agent-jobs-<agent>-<id>.scope`: systemd sends SIGTERM to every process in the unit's cgroup, waits `TimeoutStopSec` (the kill grace, 10 s), sends SIGKILL and returns when the cgroup is empty; a unit already collected (the wrapper exited) is fine; a `failed` unit only when its cgroup is gone or empty. The unit name is recomputed from the agent and the job id, never read from the job dir. If systemctl cannot stop it (no user bus, the manager busy), the daemon sweeps the scope's cgroup itself (`/user.slice/user-<uid>.slice/user@<uid>.service/app.slice/<unit>`, the same pidfd rounds as the wrapper) and accepts the stop only when the cgroup is then gone or lists no live process. If that fails too, the stop is recorded as pending on the row (`scope_pending`) **before** the row turns terminal, the job is failed with «processes survived the job (scope not stopped, retried every tick: …)» (cancel keeps `cancelled`, timeout keeps `timeout`, with that note), timeout/cancel also fall back to the process-group kill below, and every tick retries the stop until the unit is gone; meanwhile the job-done line, `status`, `list` and `job_status` say «stop pending» and the worktree cleanup waits.

**Process-group kills** (timeout, cancel without a scope, or when the scope stop failed). `wrapper.json` lies in the job dir, which the job can write, so a pgid is never trusted: before any signal the daemon requires pgid > 1, pgid ≠ its own process group and `getpgid(wrapper pid) == pgid`; otherwise it refuses and logs (the row is still finished). Adoption from `wrapper.json` refuses a pgid ≤ 1, the daemon's own group, or a live pid that does not lead that group (the job then fails after the launch grace).

**Cleanup** (repo jobs only; empty work dirs are left for the future `prune`). First the ownership check: `<jobdir>/work` is a real directory (not a symlink), `worktree.json` path matches, the path is registered in `git worktree list --porcelain` of the source repo, its admin gitdir lies under `<repo common git dir>/worktrees/`, equals the one recorded at creation and carries this job's owner mark (`agent-jobs-owner`) – otherwise nothing is touched. Then the driver check: if the repository-level config (scopes `local` and `worktree`, includes followed; read with `git config --list --show-scope`) names a filter driver (`filter.*`), a diff driver command (`diff.*.command`) or a textconv (`diff.*.textconv`), any diff would run that program in the daemon, so no patch is made: `diffstat.txt` holds one line saying why, the worktree is kept for a human, the ref `refs/agent-jobs/jobs/<id>` is still set, the reason is logged and the job counts as cleaned (not retried). The daemon owner's global/system config (e.g. `filter.lfs`) does not count. Otherwise, without modifying the index or files: `diffstat.txt` = `git diff --stat <base>` + untracked list, `commits.patch` = `git format-patch <base>..HEAD --stdout`, `staged.patch` = `git diff --cached --binary HEAD`, `uncommitted.patch` = `git diff --binary HEAD`, `untracked.tar` = untracked, not ignored files (`git ls-files --others --exclude-standard`). Restore: in a fresh worktree checked out at `<base>`, with `J=<jobdir>` (empty patches are skipped – git rejects an empty patch; tested for only commits / only staged / only unstaged / only untracked / all / nothing):

<!-- restore -->
```sh
set -e
[ ! -s "$J/commits.patch" ] || git am "$J/commits.patch"
[ ! -s "$J/staged.patch" ] || git apply --cached "$J/staged.patch"
[ ! -s "$J/uncommitted.patch" ] || git apply "$J/uncommitted.patch"
tar -xf "$J/untracked.tar"
```

Then `git update-ref refs/agent-jobs/jobs/<id> <job HEAD>` in the source repo, then `git worktree remove --force <jobdir>/work` – only that path. Any failure before the removal keeps the worktree and retries next tick.

## Launch command (reference, except DEVIATIONS #15)

```

  --max-turns N --max-budget-usd B \
  --permission-mode bypassPermissions \
  --settings <jobdir>/settings.json --setting-sources project \

## Codex runner (DEVIATIONS #5)

A job runs on `codex exec` instead of `claude -p` when its model starts with `gpt-` (e.g. `gpt-6.1-sol`, `gpt-6-astra`) or the request says `runner: codex` (`agent-jobs start --runner codex`); the default runner stays claude. `runner: codex` with a non-`gpt-` model, or `runner: claude` with a `gpt-` model, is rejected. The kind × complexity table (DEVIATIONS #6) is unchanged; config `models` (`{"review": {"hard": "gpt-6.1-sol"}}`) overrides single cells, and a `gpt-` cell routes those jobs to codex. The row records `runner` and `reasoning_effort`.

```
codex exec --json --ignore-user-config --ignore-rules --ephemeral --skip-git-repo-check \
  -s read-only|workspace-write -c 'approval_policy="never"' -c 'mcp_servers={}' \
  [--add-dir <jobdir>/progress]  # workspace-write only (issue #92)
  [-c sandbox_workspace_write.network_access=true]  # workspace-write with codex_write_network: true (default off)
  --disable apps --disable browser_use … --disable hooks \
  -m M -c model_reasoning_effort=E - < prompt.md
```

Progress file (issue #92): `workspace-write` makes only the work dir (and the temp dirs) writable, so the preamble's `<jobdir>/PROGRESS.md` cannot be written by a codex job. A write kind (fix, general) therefore gets `<jobdir>/progress/` (`CodexProgressDir`, created by `prepare` as a real 0700 directory) as its one extra writable root, and `codexPreamble` swaps the preamble's progress bullet for one naming `<jobdir>/progress/PROGRESS.md` (`CodexProgressPath`); a read-only kind gets no root and a bullet saying it keeps no progress file. The wrapper (`codexArgvSandbox`, `admittedCodexAddDirs`) admits `--add-dir` only once, only under `workspace-write`, only as exactly that folder's absolute path, and only when it is a real directory. Codex jobs are never auto-continued and get no stop report, so the daemon does not read this file; it is for the orchestrator.

Commits (issue #92, `codex_commit.go`): under `workspace-write` codex keeps the repository's git dirs read-only, the worktree's admin dir (`.git/worktrees/<name>`, with the index; codex resolves a `.git` pointer file and protects the gitdir it names) and the common dir, whose `objects/` a commit writes. Opening the admin dir as another `--add-dir` would not be enough, and opening the common dir would let the job rewrite every branch's refs and objects of the owner's repository. So a codex write job leaves its changes in `work/` and its message in `<jobdir>/progress/COMMIT_MSG` (`codexPreamble` says so), and the wrapper, after the run and a complete sweep, commits once (`commitCodexWork`): `git --git-dir=<worktree.json gitdir> --work-tree=<jobdir>/work` with the job's `GitEnv` (job gitconfig, no hooks, fsmonitor, pager or editor), `status` → `add -A` (ignored files stay out) → `commit --no-verify --cleanup=strip` with `commit.gpgSign=false` and `user.name` / `user.email` from `git_name` / `git_email` when set. The message is `COMMIT_MSG` read without following a link (control characters dropped, at most 8 KB) unless it is blank or names an owner (`owner_names`; an unreadable config counts as a match), else a default naming the job. A repository config naming filter or diff drivers (`driverKeys`, as in Cleanup) skips the commit; so does a nested `.git` anywhere below `work/` (`nestedGitDir`, checked before any git command: git runs a submodule's status with the submodule's own config and without the `GIT_CONFIG_COUNT` overrides, so a filter driver the job put there would run in the wrapper; `status` also passes `--ignore-submodules=all`), and any git failure. Either way the result is a `run-wrapper: codex commit…` line in `stderr.log`, and uncommitted changes still reach `uncommitted.patch` / `untracked.tar` at cleanup. Only `workspace-write` launches get this: under `danger-full-access` the job can commit itself, read-only kinds write nothing.

Network (issue #92): `workspace-write` blocks the network of the job's commands by default (`npm ci` failed with `EAI_AGAIN`). With config `codex_write_network: true` (absent or `false` = off; an owner opt-in, since with network the job's commands reach anything and can send out whatever the job can read) a `workspace-write` launch adds `-c sandbox_workspace_write.network_access=true` (`CodexNetworkOverride`; the key of codex-cli 0.162.1's `sandbox_workspace_write` table); read-only launches never do, and `danger-full-access` (`worktree-full-access`) is not network-confined by codex at all, so `codex_write_network: false` does not keep it offline. `authorizedLaunchConfig` treats it like `codex_write_allowed` (a `false` on disk revokes it at once; turning it on needs a restart), the launch authorization records it (`launch_authorizations.codex_network`), and `codexArgvSandbox` admits exactly that override once, which `admittedCodexNetwork` accepts only under `workspace-write` with the recorded authorization; every other `sandbox*` key stays refused.

Isolation: a codex job never inherits the owner's codex setup. `--ignore-user-config` drops `~/.codex/config.toml` (and with it the owner's MCP servers, apps, plugins, profiles and approval settings), `--ignore-rules` drops the owner's rules files, `--ephemeral` writes no session files, `approval_policy="never"` keeps it non-interactive, `mcp_servers={}` leaves no MCP server, and `--disable <f>` turns off every feature in `CodexDisabledFeatures` (`internal/jobs/codex.go`: `apps`, `browser_use`, `browser_use_external`, `browser_use_full_cdp_access`, `computer_use`, `image_generation`, `multi_agent`, `plugins`, `plugin_sharing`, `remote_plugin`, `skill_mcp_dependency_install`, `daemon_auto_start`, `in_app_local_automation`, `goals`, `realtime_conversation`, `worktrees`, `hooks`). An inherited write-capable MCP tool, app or plugin would act outside the shell sandbox; without them the sandbox is the whole containment. The exact command line was run by hand on codex-cli 0.162.1: it authenticates, and the stray MCP transport error seen without these flags is gone. Turns = completed items other than reasoning and `error` items, which are warnings such as ignored config settings (agent messages, commands, file changes, tool calls), and the wrapper logs the token usage from `turn.completed` to `stderr.log`.

Terminal event rule: a codex job succeeds only when its stream ends in a completed turn. The parser reads `stream.jsonl` line by line with a bounded buffer: a line over 8 MiB (a huge command output) is skipped and counted (logged to `stderr.log`), never held whole, and the lines after it still count; a read error is kept. A `turn.started` voids an earlier turn end, so a stream cut inside a later turn has no end. The verdict: exit ≠ 0 = «codex exited with code N»; `turn.failed` as the last turn end = error; a read error, or no terminal `turn.completed` (codex stopped early, the stream is truncated) = failure, also with exit 0.

Report: when the job did not write `report.md` itself and the stream ended in a completed turn, the wrapper writes the text of the last `agent_message` item as `report.md` (in a read-only sandbox the job cannot write it, so this is the normal path); an earlier message of a stream without a terminal `turn.completed` never becomes the report. With neither the job fails «exit 0 without a report», as a claude job does.

Resume of a codex job is refused (`job_resume`, `agent-jobs resume` and the launch): the resume subcommand exists (`codex exec resume`, codex-cli 0.162.1), but resume stays refused for now: it is not verified under the job's containment yet. A codex job stopped while still queued never ran and can be requeued as usual.

**Known limit: no guard inside codex.** The guard hook, the `settings.json` deny rules and the job MCP server are Claude Code features; codex runs none of them, so nothing inspects a codex job's commands (no push/tag/gh refusal, no nested-agent rule, no subagent cap, no `memory_*` tools). The codex sandbox is the containment: `read-only` forbids writes and, by default, network access. Therefore a `workspace-write` codex job (kind `fix` / `general`) is refused at enqueue and again at launch unless config `codex_write_allowed: true` (default false): by default only read-only codex jobs (review, research) run. Authorization before launch: every codex launch reads and validates `config.json` again and requires both the active daemon permission and the disk permission for workspace-write. Enabling `codex_write_allowed` requires a daemon restart; a queued write job whose `codex_write_allowed` was turned off on disk meanwhile, or any codex job while `config.json` cannot be read or is invalid, fails «refused to start: …» and codex never runs. The active daemon config supplies the codex binary and the default effort of that launch. Turning it on means accepting a job that can write in its worktree without the guard.

**Prune** (`agent-jobs prune [--dry-run]`; the lifecycle lock is taken per job and the row re-read under it – a job resumed or changed since the listing is left alone – so a long prune never holds up the ticks between jobs). For every terminal job with `finished_at` older than 48 h: the job folder must be a real directory (else untouched); a repo job without `cleaned_at` is skipped (its patches are not saved yet). Each top-level entry is judged by `lstat`: the records `report.md`, `base_commit`, `diffstat.txt`, `commits.patch`, `staged.patch`, `uncommitted.patch`, `untracked.tar` always stay; other regular files stay when ≤ 1 MiB and text (no NUL, valid UTF-8 in the first 8 KiB, read `O_NOFOLLOW|O_NONBLOCK`); everything else goes – subdirectories (work dir, caches, builds, `no-hooks/`), binaries, large files, special files, symlinks (unlinked, never followed). Exception: `work/` of a repo job that still has a `.git` (the worktree cleanup kept for a human) stays. Removal never follows links (`os.RemoveAll`); read-only directories left by a job are made writable first (also the job folder itself). Before the entries are judged, the job's records move into the log archive (below); if that fails (a symlinked archive path, a full disk) `stream.jsonl` and `stderr.log` stay, the rest of the folder is still judged and cleaned, and the error is reported. After the jobs, archived months past the retention are removed. A second pass finds nothing.

**Log archive** (`internal/jobs/archive.go`; part of every prune, alone as `agent-jobs archive [--dry-run] [--json]`, under the lifecycle lock). Same jobs as prune (terminal except `stopped`, finished > 48 h, real job folder, repo jobs only after cleanup). Destination `<archive>/<YYYY-MM>/<id>/`, the month being the UTC month of `created_at`, so every attempt of a job maps to one dir (an archive an earlier build put under the month of `finished_at` is still found and used); `<archive>` = config `log_archive_dir` (absolute) or `<state>/archive`. The root, the month dir and the job dir are checked with `lstat`: a symlink is refused (never followed) and fails the job's archive; the root is created 0700 with a marker file `.agent-jobs-archive` and a root holding the marker is kept 0700 (the logs carry tool output). An existing root without the marker (a folder the owner already uses) is archived into but never chmodded or expired; prune and `agent-jobs archive` then print `retention off: no marker in <root>` (JSON `retention_off`) while `log_archive_days` > 0. The default root `<state>/archive` belongs to agent-jobs: a pass that writes gives it a missing marker back (one left without it by an earlier build or by a marker write that failed after the mkdir). When the archive of a job fails (a refused path, a full or missing disk), prune keeps `stream.jsonl`, `stderr.log`, `attempts/` and the copied records (`prompt.md`, `report.md`, `diffstat.txt`), still cleans the rest of the folder and reports the error. Before the build, temporary dirs `.<id>.tmp-*` of this job left by an interrupted pass are removed. The archive is built in a temporary dir `.<id>.tmp-*` next to its destination and renamed into place, so a half-written archive is never taken for a finished one: `stream.jsonl`, `stderr.log` and `stream-resume-failed.jsonl` gzipped, `prompt.md`, `report.md`, `diffstat.txt` copied, `meta.json` = the job row without the launch token, `attempt` included (the brief is in `prompt.md`); for a resumed job also `report.attempt-<n>.md` copied and, per earlier attempt (only `n` below the row's `attempt`: a higher `attempts/<n>/` is the job's own and is neither archived nor counted in the stats), `attempts/<n>/` with `stream.jsonl`, `stderr.log`, `stream-resume-failed.jsonl` gzipped and `resume.md`, `fallback.md` copied. Sources are opened `O_NOFOLLOW|O_NONBLOCK` and copied only when the opened fd is a regular file; outputs (`meta.json` and the marker included) are created `O_EXCL|O_NOFOLLOW` 0600 and fsynced; the temporary dir is fsynced before the rename, the month dir and the root after it. After the rename the gzipped originals are removed from the job folder (`report.md`, `diffstat.txt`, `prompt.md` stay there as before). A job already archived is not archived again, and a job with an archive dir can no longer be resumed (`job_resume` and the launch refuse it: «archived by prune; start a new job»), so a later attempt never needs archiving next to an earlier one; leftover originals of an interrupted pass are removed only when the destination holds `meta.json` and the `.gz` copy of each of them (an emptied or partial destination keeps them and reports an error). The job folder is made 0700 first if the job made it read-only (also for `agent-jobs archive` alone). Retention (roots with the marker only): config `log_archive_days` (default 365, 0 = forever); a top-level `<YYYY-MM>` entry whose month ended more than that many days ago is removed (a symlink as a link); other entries are left alone. Prune runs the retention before its per-job pass, so a pass cut short by its context (the daily time-box) never starves it. The archive lies outside `jobs/`, so cleaning job folders never touches it; an external backup of the state dir (a nightly restic or rsync of the home dir) carries it off the machine.

**Job stats** (`internal/jobs/stats.go`, table `job_stats`). One row per job, written right after a terminal status is recorded (collect, timeout, cancel, stop, a refused launch; all under the lifecycle lock); a resumed job keeps its one row, rewritten at the end of every attempt with the totals of all attempts so far (turns, cost and duration from the `attempts` table plus the row, tool calls, skills, refusals and subagents from every attempt's stream, `attempts/<n>/` included; status, report and result subtype of the latest attempt), so a resume never counts an attempt twice and a stopped job shows as `stopped` until its next attempt ends, and by prune before a job's stream moves to the archive if the row is still missing; a failed write is logged and left to `agent-jobs stats --backfill`. The wrapper is not involved. Columns: id, kind, model, status, turns, cost_usd, duration_sec (from the job row), created/started/finished, repo (basename only), tool_calls (JSON, by tool name; subagents' calls included), skills (JSON, by name: `Skill` tool calls and `Read`/`Glob`/`Grep` under a `skills/<name>/` dir), guard_refusals and guard_rules (JSON, by rule: an `is_error` tool result carrying a `blocked by guard:` / `agent-jobs guard:` message, mapped to a rule name by `guard.RuleName`), subagents (Agent/Task calls the guard did not refuse, at least the store's counter), has_report (non-empty `report.md` in the job folder or the archive), result_subtype (last `result` event), source (`job_dir`, `archive`, `none`). The stream is read from `<jobdir>/stream.jsonl` or `<archive>/<YYYY-MM>/<id>/stream.jsonl.gz` (both `O_NOFOLLOW`), streaming, a line at a time; lines over 8 MiB are skipped without being held. `agent-jobs stats --backfill [--all]` writes the missing rows (every row with `--all`) under the lifecycle lock. `agent-jobs stats [--since D] [--by kind|model|skill] [--json]` and the `job_stats` tool aggregate: totals and per-group jobs, counts by status, success rate (succeeded / jobs), cost total, median and p90, duration median and p90 (nearest rank), turns, refusals, subagents, jobs without a report; the top 20 guard rules and tools; skills by uses with the jobs that used them and their success rate. With `--by skill` a job counts in every skill it used, jobs without one under `(none)`.

**Skills for jobs** (E7 job-side part, DEVIATIONS #16; `internal/skills`, `internal/jobs/skills.go`). agent-jobs ships no catalog and names none: config `skill_roots` lists absolute directories, each holding `index.json` (`{"version", "skills": [{name, place, path, status, kinds, projects, owner, origin, last_verified, sha256, size_kb, has_scripts, risk}], "plugins"}`; any tool may write it, e.g. a skills git checkout; only name, path, status, kinds, projects and risk are typed, the informational fields are free-form (`origin` a string or an object; a value of another type reads as empty) and unknown fields are ignored; entries are decoded one by one, so an entry malformed in a needed field is skipped with a warning naming it, never its root). `skills.Load` reads every root in order on each use (a missing or invalid root, or entry, is a warning: `agent-jobs status`, `system_doctor` `skill_warnings`); an entry is kept only if its name is a plain name, its status is `core|active|draft|deprecated`, its `path` is relative and, symlinks resolved, a directory strictly inside the root named like the skill, with a regular `SKILL.md`, and every symlink in its tree resolves to a regular file inside the skill's own directory (a symlink to a directory, to another skill, elsewhere in the catalog or beyond, dangling or looping rejects the entry: a job may follow every link, and a directory link could lead anywhere through further links); its size is measured on the directory (regular files and the targets of file symlinks), not taken from the index; the first root wins a duplicate name. A root that is `/`, holds the agent state or lies inside it is skipped. **Selection** at `job_start` (`newJob`, also for schedules at each firing): the `core` entries whose kinds meet the job kind (`fix`/`general` -> `code`, `general`; `review`; `research`; the kind itself) plus the `core`/`active` entries whose `projects` name the repository's folder; edits `name`/`+name` add (a `draft` only this way), `-name` removes; an unknown name (with up to five close names: edit distance at most 2, a substring or a 3-letter prefix), a deprecated one, more than `skills_max_per_job` (default 6, ceiling 8) or more than `skills_max_kb` (default 400) refuses the start. The sorted names are stored in `jobs.skills`. **Delivery** (`deliverSkills`, in `prepare` after the worktree exists and in `prepareResume` after the `.claude` check, before `settings.json` is written): the catalog is read again, each skill re-validated and the budget re-measured; `skills.Link` creates `<work>/.claude` and `.claude/skills` as real directories when missing (a symlinked one refuses), skips a name the work dir already has (the repository's own skill wins; `jobs.skills_note`), except a link an earlier attempt left behind (`leftSkillLinks`: a symlink at a name of the row's `skills_delivered` that resolves into a usable catalog root), which is adopted as delivered (re-pointed when its target changed), and creates `<work>/.claude/skills/<name>` -> the absolute catalog directory; the repository's `info/exclude` (`git rev-parse --git-path info/exclude`, the common dir) gets a block `# agent-jobs <id> skill links ...` with `/.claude/skills/<name>` per link (no trailing slash: git sees a symlink as a file); every update of that shared file (adding and removing a block) holds an exclusive flock on `<common git dir>/agent-jobs-exclude.lock`, so jobs of one repository in any process rewrite it one at a time. Until the new list is recorded the row's earlier list stays in memory, so a failed delivery still lets the removal retry links left behind. The linked names go to `jobs.skills_delivered` (token-bound). A codex job records «skills not supported for codex runner» and links nothing. The brief carries one line after the preamble naming the job's skills. **Protection**: `settings.json` denies `Edit`/`Write`/`MultiEdit`/`NotebookEdit` on `//<root>` and everything below it (configured and resolved) and on every link; the guard gets the same paths as `--protect`, so Bash writes, redirections, `rm -r`, `cp` into them are refused like agent-jobs state (reads stay allowed). **Removal** (`removeSkills`, idempotent): when the attempt ends (`finish`: collect, timeout, wrapper death; `Stop`; `Cancel`; a refused launch) and again at the start of `Cleanup`, before any diff, patch or untracked list is made: only symlinks at the recorded names are removed (never followed; a real file there stays), then `.claude/skills` and `.claude` if empty, then the job's exclude block. A link that cannot be removed (`skills.Unlink` returns it with the error) keeps its exclude line and its name on `skills_delivered`; when `.claude` or `.claude/skills` cannot even be inspected (e.g. `.claude` unreadable), every recorded name is returned as left, since the links may still be there; the block goes only when every link is gone. The resume `.claude` check ignores such a left link (an `!!` or `??` status line of exactly that path, so also when its exclude line went missing, as long as `leftSkillLinks` finds it a symlink into a usable catalog root at a recorded name; without a repository a `.claude` holding only `skills/` with those links), the next attempt adopts it, `Cleanup` retries the removal. So the links never reach a commit made with `git add -A`, a patch, `untracked.tar` or the resume check. **Result check** (`checkSkillLinks`, in `finish` once the scope is stopped): info/exclude does not stop `git add -f`, so the index (`git ls-files --cached`) and the commits since the base (`git log --name-only base..HEAD`) must not contain a delivered link path `.claude/skills/<name>`; otherwise the attempt fails with «the job staged or committed its skill link …» (a timeout keeps its status and gets the note; a failed check fails closed). The guard already refuses `git add -f` naming a link (a protected path argument); a whole-tree `git add -f -A` or `git add -f .` names none and is caught by this check. **Stats and rating**: `job_stats.skills_delivered` (names); `stats --by skill` shows delivered and delivered-but-unused next to uses; `Manager.SkillRatings` (`GET /v1/skills`, `stats --by skill --by-repo`) gives per skill the catalog status (`not_in_catalog` when gone), delivered and used counts, success rate, last use, median known cost and a per-repository breakdown, sorted by used count; `stale` = `last_verified` missing or older than 90 days, or the last use (or, never used, the verification) older than 60 days. **Search** (`Catalog.Search`): BM25 (k1 1.2, b 0.75) over one weighted bag of terms per entry: name x3, front matter description x2, kinds and projects x1.5, the first 4 KB of the `SKILL.md` body x1; terms are lowercase runs of letters and digits of any script; a document term that starts with a query term of 4+ runes counts at half weight (word forms); ties by name.

**doctor procs** (`agent-jobs doctor procs [--kill]`, Linux `/proc`, processes of this uid, never this process or its ancestors). *Job ghosts*: a process whose environment carries `AGENT_JOBS_JOB=<id>` of a job in this agent's store that is finished or whose wrapper is dead (an id the store does not know – another agent's job – is not judged); or a process whose session id is the recorded pgid of a finished job and whose session leader no longer exists (a running row whose wrapper died is matched by marker only: its window has no end, so a later session reusing the id would match). Either way the process must have started inside the job's run window `[StartedAt-1s, FinishedAt+1s]` (start time from `/proc/<pid>/stat` + `btime`; no upper bound for a running row whose wrapper died), and a job that started before the current boot owns nothing. For a session the earliest-started live member of the session (any uid: the kernel keeps a session id allocated while any member lives) must be inside the window too, so a reused session id whose first member predates or postdates the job is not the job's. *Leaders*: a marked process inside the window that leads its own session (`sid == pid`, it daemonized – a tmux server whose environment, and every later pane, carries the marker); also a marked process whose session leader is alive and is not the job's recorded pgid, or that has a marked `sid == pid` ancestor other than the job's wrapper (it runs under such a daemon, e.g. in a tmux pane); reported, never killed. *Suspects*: a process whose session leader is gone and whose command line is a browser (chrome, chromium, headless_shell, playwright, firefox, …), a preview server (vite, next dev, http.server, serve, storybook, `npm run dev`, …) or a shell wait loop (`while`/`until` with `sleep`/`pgrep`/`kill -0`). *Dead rows*: running rows whose wrapper pid is dead, or claimed rows that never registered a wrapper after the launch grace. Report only; `--kill` signals job ghosts only, never leaders or suspects (DEVIATIONS #13): a pidfd is opened first, the start time and session are re-read and must equal the scanned ones, then SIGTERM, 3 s, SIGKILL through the descriptor; a changed identity or no pidfd = not signalled.

**Daily automation** (`internal/jobs/daily.go`; reference «Раз в сутки jobs prune…», «Раз в сутки проверка призраков»). No timer of its own: after every tick the daemon loop calls `StartDaily`. A run is due once per local calendar day at the first tick at or after `daily_hour` (default 4, local time; `daily_off: true` disables). `Store.ClaimDaily(day)` is one atomic upsert that succeeds only when the stored day is earlier (a clock or TZ step backwards never re-runs a day), so a restarted daemon (or a second one) never repeats the day, a run that crashed still counts, and a missed day runs once at the next tick after the hour – never more than once a day, no catch-up. Not started while the daemon shuts down; a process-local mutex (`TryLock`) means two runs never overlap (a day reached while the previous run hangs is not claimed and runs once that run ends). The run is a goroutine, so the tick loop goes on launching jobs: (1) `PruneContext` for real (with the log archive), bounded by 10 minutes (`DailyStepTimeout`) and the daemon context – it stops between jobs; (2) `DoctorProcs(false)`, report only (`--kill` stays manual), bounded the same way; a failing step never skips the other, a panic is recovered (also one in the doctor procs scan, which runs in its own goroutine and is recorded as `doctor procs panicked: …`). The scan has no cancellation points: at the time-box it is abandoned, and it keeps the daily lock until it really ends, so the next day's run never overlaps it. The summary (jobs pruned, bytes freed, jobs archived and bytes, archived months expired, ghosts by kind, dead rows, errors) is logged at info level and stored as JSON in the `daily` row; `agent-jobs status` without an id and `system_doctor` (`daily`) show it. On shutdown the daemon cancels the run and waits for it before closing the store, except an abandoned doctor procs scan, which is not waited for (waiting could hang shutdown); it only reads `/proc` and the store, and a store closed under it makes it fail, not write.

**Schedules** (`internal/jobs/cron.go`, `internal/jobs/schedule.go`, `internal/store/schedules.go`; PLAN Wave B). Inside every `Tick` (under the lifecycle lock, before launching): each enabled schedule whose cron matches the current minute on the local wall clock (`Manager.Loc`, default `time.Local`) is claimed with `Store.ClaimScheduleFiring` – one `UPDATE` that succeeds only when this minute is strictly later than the last firing both as `last_fired_at` (absolute) and as `last_fired_local` ("YYYY-MM-DD HH:MM", compared as a string: an increasing local watermark), so a restarted or second daemon never fires twice, a clock step back never re-fires, and in the hour repeated at the end of DST nothing fires again until the wall clock passes the last firing (`*/30 2 * * *` fires at 02:00 and 02:30 once each, not in the second pass); a wall-clock minute skipped by spring-forward never matches. `schedule_list`'s `next_fire_at` (`Manager.NextFire`) skips due minutes the watermark would suppress, so it never advertises one. `Cron.Next` walks calendar days in UTC (each step a new date, at most 30 years of days, else an error), checks the candidate's full date and time in the local zone, and takes the earlier of both instants of an ambiguous wall time; a zone that springs forward at midnight (America/Havana) cannot hold it. A claim counts before delivery: a missed minute (daemon down, no tick in it) or a failed delivery is lost, never queued; the outcome (`last_job_id`, `last_error`) is recorded on the row. Cron: 5 fields, `*`, values, `a-b`, `/n` steps (`a/n` = a to the maximum), comma lists, `jan…dec` / `sun…sat`, weekday 7 = Sunday, `@hourly` `@daily` `@midnight` `@weekly` `@monthly` `@yearly` `@annually`; day-of-month and day-of-week match either when both are restricted (neither starts with `*`), both otherwise; an expression that never fires (30 February) is refused. Prompt: valid UTF-8, no control or format character (newline, escape, bidi), ≤ 2000 runes (refused, not cut), then `Printable` and the `[jobs:` defang of notify_owner. Delivery without a kind: the session schedules due in one tick are typed through `sendTmuxLocked` (the job-done and notify_owner path: `tmux.lock`, bounded by `TmuxDeliveryTimeout`, process group killed at the deadline, trailing `;` kept literal) as one line, `[jobs:schedule] schedule <id>: <prompt>` or `[jobs:schedule] these are different instructions, do each one: 1) schedule <id>: … 2) …`; a session schedule needs `notify_tmux_target` at creation. With a kind: at creation the job fields are validated by the same code as `job_start` (`newJob`: kind, limits, model or complexity, runner, codex rules, repo, base) and the resolved model, runner, reasoning effort and limits are stored; at firing `Enqueue` runs with them (the brief is the prompt, `schedule_id` set; the base ref is resolved again; config is re-checked, so a codex write kind turned off later fails the firing), and the session sees only the job-done line. Rows never expire; `schedule_set` edits cron, prompt and enabled in place; `schedule_remove` deletes (jobs keep their `schedule_id`).

**Checks** (dead-man's switch; `internal/jobs/checks.go`, `internal/store/checks.go`; PLAN Wave B). A check is a name, a cron in local time (the schedules' parser; one that never fires is refused) and a grace in minutes (default 60, 1..10080); `armed_at` (the arm time A) is set at creation and moved to now when `check_set` changes the cron or the grace or enables the check: a configuration epoch. Every `check_set` bumps `revision`. Marks (`check_mark`, `agent-jobs check mark`) are rows in `check_marks` (unix seconds, note, job id).

*Mark ownership* is a pure function of the mark time m and the check's cron, grace and A – no consumption state, no ordering by insertion id, independent of downtime and insertion order. The expected times are the cron's due instants E > A (strictly after: an expected time at the arm instant would leave the watched work no time), minus repeated wall-clock minutes (a due instant in the second pass of an interval repeated when DST ends is skipped, the schedules' watermark rule; the transition is found by bisecting the zone offset, so no cron search walks the fold). With P(E) the previous expected time (A for the first E), owner(m) is the earliest E with m > P(E) and m ≤ E+grace; equivalently the earliest E > A with E ≥ m−grace, and E's owner window is (P(E)+grace, E+grace], the first one [A, E+grace]. The windows partition the time from A on, so every mark at or after A has exactly one owner and a mark before A none (it never counts). E is satisfied iff at least one stored mark has owner(m) = E (`Store.MarkTimes` over the window). Examples, hourly cron, grace 60: (1) created 09:01, one mark 09:59 – the first E is 10:00 with window [09:01, 11:00], so E=10:00 is ok; (2) created 09:00, the only mark at 10:59, the daemon back at 12:00:01 – owner(10:59) = 10:00 (10:00+60m ≥ 10:59), so E1=10:00 is ok and E2=11:00 (window (11:00, 12:00]) is missed.

*Evaluation.* Inside every `Tick`, under the lifecycle lock, after the schedules: for each enabled check the watchdog walks every unevaluated E in chronological order – from the one after the evaluation watermark `eval_at` (or the first E after A when `eval_at` is not after A: a watermark of an earlier configuration) up to the latest with E+grace+1 s ≤ now (the extra second: a mark stored in E+grace's second, unix seconds, is already in the store), at most `MaxCheckEvaluationsPerTick` (1000) per check and tick, the rest the next tick. `latestFire` finds the latest due instant ≤ t with a doubling search and a binary search over `Cron.Next` (bounded whatever the expression). The marks of all those windows are read once and each E judged from them; `Store.ClaimCheckEvaluations` stores the batch in one `BEGIN IMMEDIATE` transaction – the watermark (`eval_at`, `eval_local`, `eval_result` of the last E) and one `check_alerts` row (pending) per missed E – that succeeds only when the check is enabled, still at the `revision` the watchdog read (a `check_set` in between voids it: no obsolete E is judged) and the first E is later than `eval_at` with its local minute later than `eval_local`, so each E is judged once across restarts and daemons, and the second pass of a repeated hour never is. A judged E is never re-judged. *Retention:* a mark is pruned only when its owner is evaluated (m ≤ `eval_at`+grace with `eval_at` > A) or it predates A; admission instead of a cap that deletes evidence: an owner window stores at most `MaxMarksPerWindow` (20) marks, later ones are accepted, update the last mark and return `mark: "ok, already marked"` (the CLI prints it), so a check holds at most 20 × its unevaluated windows marks, which the bounded evaluation keeps bounded.

*Alerts* (`check_alerts`: expected time, state pending/delivered/failed, attempts, next attempt, attempt token, error, merged counter, acknowledged). A missed E's row is never replaced by a later miss; each row keeps its own attempts and backoff (1, 2, 4, 8 minutes), so an every-minute check with an unavailable target still brings its old rows to failed after `MaxCheckAlertAttempts` (5). At most `MaxPendingAlerts` (50) pending rows per check: beyond that the oldest are deleted and their count merged into the newest pending row's counter (its attempts untouched); likewise at most 50 failed rows not acknowledged, and the newest 50 delivered or acknowledged rows are kept as history. Delivery (`deliverCheckAlerts`) runs at the end of `Tick` after the lifecycle lock is released: `claimCheckAlerts` claims the next attempt of every due pending row under one fresh token (`Store.ClaimCheckAlertAttempt`: attempt counter, next-attempt time and token in one conditional `UPDATE`, so two daemons never make the same attempt and an attempt cut short by a crash is retried after its backoff; a row that already made 5 attempts is failed with `delivery interrupted`); `sendCheckAlerts` then fences the attempt: under `tmux.lock` it re-reads the rows still pending with that token right before typing (a stale attempt – paused past its backoff while another daemon claimed the rows again or delivered them – finds none and types nothing), types one line (`[jobs:check-missed] a expected … (no mark within 60m); b: 3 missed, latest … (no mark within 30m)`, a check's rows collapsed into one part) and records delivered (by row id) or the error (rows still holding the token; failed after the 5th attempt) before releasing `tmux.lock`. No `notify_tmux_target` is a failed attempt like any other: five, then failed. A failed delivery that could not take `tmux.lock` typed nothing and is recorded the same way. At-least-once: a crash between typing and storing delivered types the line again. Failed rows stay in `missed_checks` until a `check_set` of that check acknowledges them (`acked`); a later E judged ok, or a later mark, does not. Disabling a check pauses its evaluation (the claim needs `enabled`; re-enabling re-arms), but already pending alerts are still delivered.

`CheckViewOf` gives the state now: the stored outcome for a judged E, a live evaluation of the latest due E's window for one not judged yet (no daemon): ok, missed (a mark after the grace sets `late_mark_at`; the E stays missed), waiting (no E since `armed_at` past its grace), disabled; the newest alert row (`last_missed_at`, `alert_state`, `alert_attempts`, `last_alert_error`, `alert_merged`, `alert_acknowledged`) and `alerts_pending` / `alerts_failed` over all rows. `agent-jobs status` and `system_doctor` (`missed_checks`, a problem each) list the checks that are missed or have a pending or failed, unacknowledged alert. The migration is additive (`ALTER TABLE … ADD COLUMN`, tolerant; the per-check alert columns of fix loop 1 stay but are unused): a missed time claimed by the first checks schema becomes the evaluation watermark and a *pending* alert when `last_alert_error` is empty (that code stored the claim before typing, so an empty error proves no delivery: at-least-once), failed otherwise; then each check's alert is copied once into `check_alerts`.

**Trash** (`internal/trash`). `trash_move` takes an absolute path without `..`, resolves its parent (`EvalSymlinks`) and requires the result strictly inside a resolved root – not a root, not an ancestor of a root, no `.git` component, not inside, equal to or containing a protected path. With no roots configured nothing is moved (fail closed; the tool says how to set `trash_roots`). Protected, whatever the roots: the agent-jobs home (every agent's state dir and job database, also the trash), the owner rules file, the agent-jobs binary (`SelfBin`, which the guard hook runs, and `os.Executable`), `~/.claude`, `$CLAUDE_CONFIG_DIR` when absolute, `~/.claude.json`. Each protected path counts as named (parent resolved, so a symlink is protected as the link) and fully resolved, and a symlink whose target resolves to a protected path is refused too. The last component is not followed (a symlink is moved as the link). It writes `<trash>/<id>/meta.json` (id, original path, time, type, size) first, opens the resolved parent and the entry dir `O_PATH|O_DIRECTORY|O_NOFOLLOW` and checks each descriptor's `/proc/self/fd` path, then `renameat2(…, RENAME_NOREPLACE)` moves the item to `<trash>/<id>/item`. Another filesystem (`EXDEV`) is refused, never copied. `trash_restore` re-runs the same checks on the original path, refuses an occupied path or a missing parent, and renames back with `RENAME_NOREPLACE`; an unknown id lists the 20 most recent entries. Trash entries are not expired automatically. macOS: the descriptors are opened `O_RDONLY|O_DIRECTORY|O_NOFOLLOW` and checked by fstat device/inode against an lstat of the directory (no `/proc/self/fd`; a swapped intermediate component is not detected there), the rename is `renameatx_np(…, RENAME_EXCL)`, and the `.git` and protected-path comparisons are case-folded (APFS is case-insensitive by default).

**Owner waits** (`internal/jobs/ownerwaits.go`, `internal/store/ownerwaits.go`, `internal/mcp/tools_ownerwaits.go`; PLAN Wave D). `job_start` `owner_waits` / `start --owner-waits` sets the job's `owner_waits` column. `DoneLine` ends such a job's line with `· owner waits` (after the resumed note).

*Record before line.* `notifyPending` calls `Store.BeginOwnerPending(id, delivering)` for an owner-waits job before `sendTmuxLocked`, so the line never reaches the session without its record; `Store.MarkNotified` then sets `notified_at` and, in the same transaction, turns the open `delivering` row into `delivered` (its age counts from then; a job without a row gets a delivered one). With notify off (no target) the row is begun as `notify_off` and the job is marked notified at once. There is one row per (job, attempt): a resumed attempt gets a row of its own (its line holds again), `BeginOwnerPending` never changes an existing row of the attempt (`ON CONFLICT DO NOTHING`: a retried delivery reuses it and never reopens an acknowledged or expired attempt, and an attempt acknowledged ahead starts acknowledged), and `MarkNotified` only turns a `delivering` row into `delivered`. `owner_replied` sets `acknowledged` instead of deleting, so whatever order the daemon (begin, deliver, mark) and the MCP server (`owner_replied`) run in, SQLite serializes the statements and a reply made after the line arrived, before or after the mark, is never undone. With a `job_id` it acknowledges every attempt of the job and pre-acknowledges the latest finished attempt in one transaction, so a reply made after a resumed attempt finished but before its line began also covers that attempt.

*Expiry.* `Manager.OwnerPending` (one transaction) sets open rows older than `owner_waits_max_hours` (config, default 6, negative refused) to `expired`, which is final: a line whose delivery keeps failing stops holding after the max age and its later retries never hold again. It then prunes rows older than the max age whose attempt can no longer be delivered (the job is gone, has a newer attempt, or is finished and notified; notify retries have no cap, so a still-pending line keeps its row), and lists the open rest, one line per job (its latest open attempt), with the job's title, status and state; the Stop hook, `owner_replied`, `agent-jobs status` (no id) and `system_doctor` (`owner_reply_pending`, not a problem) all go through it, so a stale record expires on the next look.

*Session binding.* `agent-jobs hook bind --agent A` is the orchestrator's SessionStart hook: it reads the hook JSON (≤ 1 MiB; `hook_event_name` must be `SessionStart`, `session_id` and `cwd` non-empty) and stores the session id in `hook_session` (`Store.BindHookSession`; startup, resume, `/clear` rebind), printing nothing (a SessionStart hook's stdout becomes context). Provenance (`Manager.BindHookSession`): a session is bound only when all hold: (a) the caller runs in the pane of the notify target, `$TMUX_PANE` equal to `tmux display-message -p -t <notify_tmux_target> '#{pane_id}'` (on `tmux_socket`, bounded by the tmux delivery timeout); no `notify_tmux_target` configured = bind refused; (b) the input `cwd`, absolute and with symlinks resolved, is `orchestrator_dir` (config, absolute, not `/`) or below it; none configured = bind refused; (c) it is not a job (below). Replacing a binding obeys the same checks, so only a new session in the same pane and directory rebinds (another project's session with the same hooks, or a stray process elsewhere, cannot take it over); a refused bind keeps the old binding. With no binding the Stop hook never blocks. A process the orchestrator starts itself in that pane and directory (its own subagent or tool call) is inside the orchestrator's trust domain and is not defended against. Chosen over taking the session from the tmux target (a pane carries no Claude session id) or from the MCP server (agent-jobs is not handed the session id there): a hook's input is where Claude Code documents `session_id`, and only the orchestrator's settings register this one. A job cannot rebind: `hook bind` goes through the `CheckNotInJobSession` refusal of every control command (a process in a running job's session fails, the binding stays).

*Stop hook.* `agent-jobs hook stop --agent A` is a Claude Code Stop hook for the orchestrator session: it reads the hook JSON on stdin (≤ 1 MiB) and validates it (`ParseStopHookInput`): a JSON object with a non-empty `hook_event_name`; for `Stop` also a non-empty `session_id` and a boolean `stop_hook_active` (a missing one is not false). Invalid or incomplete input (empty, `null`, `{}`, a missing or mistyped field) is an error. With `stop_hook_active: true` (the session already continues after a block) or another event it allows without opening the store, so it blocks at most once per turn and never loops. Then it allows unless `session_id` equals the bound session (no binding: allow). Otherwise, while a record is pending, it prints `{"decision":"block","reason":"…"}` (the jobs with their state – line arrived, being delivered, or notify off and no line – «write the result to the owner, then call owner_replied») and exits 0; nothing pending: no output, exit 0. Every error (bad flags, bad input, the store, a job session) allows the stop with exit 1 and a stderr line (exit 2 would block). agent-jobs never edits a settings file; the README has the snippet for both hooks.

*Brief reminder* (Wave F, F9 (c)). `agent-jobs hook brief-reminder --agent A` is a `UserPromptSubmit` hook (`ParseUserPromptInput`: event `UserPromptSubmit`, non-empty `session_id`, optional `cwd`). `Manager.BriefReminder` returns nothing unless the session is the one `hook bind` stored (`StopHookHolds`); for it, one line: `SizeRuleNote` and the checklist state of the repository at `cwd` (`ChecklistRepo`, `checklist.Read`, redacted `Parse`, `ChecklistStatus`, the check `checklist_get` makes), read without the checklist lock so a prompt never waits for it. `runHook` always exits 0 for it: an error goes to stderr and no line is printed.

*Merge gate* (Wave F, F9 (b)). `agent-jobs hook merge-gate --agent A` is a `PreToolUse` hook on `Bash` (`ParsePreToolUseInput`: event `PreToolUse`, a `tool_name`, for Bash a `tool_input.command` string). `guard.GhPrMerges` reads the command with the guard's shell reader and returns its `gh pr merge` calls (the named repository from a PR URL or `-R`, the `GH_REPO` values, the directories the call may run in (`GhPrMerges(cmd, cwd)`, `mergeDirs` with the guard's `cdView` rules: followed exactly along an `&&` chain, a union of every directory reached so far where the control flow forks (`;`, `||`, `&`, subshells, groups, keywords, pipes), `RelDirs` the ones reached by a relative `cd` from another candidate, told only when no command but a `cd` or a no-op runs before the call; `sameShellChanges` makes a `cd` in `eval` / `trap`, a loop or a function unsure, `shellOptions` a physical `cd`), `--match-head-commit`, `--auto`, `--disable-auto`, why a call cannot be read) and why the command might hide one (a form the guard cannot verify counts only when `mergeText`, the text with continuations joined, quotes and backslashes dropped and case folded, names gh or merge as a word; with gh in it also `shopt`, `-O`, an unsafe `set` option or an extglob pattern; `GhPrMerges` reads strictly, PR #78's reading plus a vague head for a brace, glob or tilde at or before the `gh pr` subcommand, and only where that finds a merge or is unsure and `relaxable` holds (the text outside `<<'WORD'` / `<<"WORD"` bodies has none of the forms whose boundaries the reader may misplace, and those bodies are the ones it found) takes the relaxed reading: a literal `gh pr` head read by its subcommand, no extglob in those bodies, a quoted `-R` / `--repo` / `--hostname` value one word). `mergeGateHook` refuses a command that runs `agent-jobs gate retire` (`guard.RunsGateRetire`, `RetireRefusal`) and allows a command without a merge or a doubt before the store is opened; otherwise `Manager.MergeGate` (read-only store, `openReadOnly`) finds the gated repositories a call may merge in (a stored approval not retired since, `store.GateRepo` / `Manager.RetireGate`, and a checklist approved now, or void now; a clone by a shared OWNER/REPO name: the names stored in `merge_gate_repos` by `checklist_set`, `ReleaseCheck` and the daemon's `BackfillGateNames` at start, plus the remotes now, so a gone work tree with stored names never makes another merge unsure; one without stored names and with unreadable remotes makes a merge by name or in another work tree unsure; a missing `RelDirs` candidate is skipped unless every candidate is one) and refuses unless the sha is a full 40-hex one with a `store.ReleasePass` at the checklist id, version and hash as they are, not older than the latest verdict for the sha or a red manifest-check record. `Manager.ReleaseCheck` writes that row on a pass and drops the repository's rows for the sha on any other answer (`releaseCheck` computes, writing nothing). Exit 2 blocks with one stderr line. A merge it cannot read (a doubt from `GhPrMerges`, a call's `Unsure`, a candidate repository it cannot identify) is not refused while any repository is gated: `MergeGateAnswer.Warning` (`warnUnsure`) is printed as PreToolUse hook JSON on stdout (`hookSpecificOutput.additionalContext` for the model, `systemMessage` for the user, no `permissionDecision`) with exit 0; an identified gated target is still checked first, so an unreadable other candidate never lifts its gate. The exception: a call whose only doubt is `guard.DynamicWordUnsure` (a variable or substitution in its words, its target literal) and whose target is a gated repository is refused (`dynamicWordRefusal`: write every word literally), also with a literal sha that has a pass, since the call does not tell which word is dynamic and an unquoted one may split into flags; a dynamic target (`-R`, a PR URL) only warns. Inside a job (main's job-role refusal, `ErrInJobSession`) it exits 0.

*Job size* (Wave F, F9 (a); `internal/jobs/size.go`). `newJob` calls `checkSize` after the covers snapshot (`coverContract`): a size other than `small` / `large` is refused for any kind; `fix` and `general` (`SizeKinds`) without a size are refused when the request carries `SizeRule` (set by the `job_start` tool and `agent-jobs start`, never by schedule firings or `StartGate`) and config `size_required` (a hot key) is on; `large` needs `covers` and every covered row live (`checklist.Row.Live`), on the checklist `coverContract` already held to the latest approval. `Enqueue` logs the size of a queued `fix` / `general` job (`logSize`), and the row keeps it in column `size`.

## Rules enforcement

What this is and is not: the deny rules and the guard block the *direct spellings* of outward actions in a Bash call, and the wrapper's git environment scrub keeps git itself from running programs the guard does not see. This is **not a sandbox**: a script the job writes and then runs is allowed by design (as in the reference), and what it does is not inspected. Within a single Bash call the guard rejects forms it cannot resolve statically around git/gh instead of guessing.

- **settings.json deny** (holds under bypassPermissions): `git push`, `git tag`, `git send-pack`, `git http-push`, attached forms `git -c*`, `git --config-env*`, `git --exec-path*`, `env -S*`, `env --split-string*`, `systemd-run`, `systemctl --user`, `busctl`, `dbus-send`, `gdbus`, `qdbus`, `qdbus-qt5`, `qdbus6`, `dbus-run-session`, `crontab`, `at`, `batch`, `tmux`, `screen`, `pm2`, `docker`, `docker-compose`, `podman`, `podman-compose`, `ssh`, `machinectl`, `loginctl`, `unshare`, `nsenter`, `gh release`, `gh api`, `gh pr create|new|comment|edit|merge|review`, `gh issue create|new|comment|edit`, nested agents `claude`, `codex`, `gemini`, `aider`, `cursor-agent`, `claude-code`, `gemini-cli`, `aider-chat`, package runners `npx`, `pnpx`, `bunx`, `uvx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bun x`, `pipx run`, `uv tool run`, file tools inside `.git` (`Edit|Write|MultiEdit|NotebookEdit(**/.git/**)`), plus the known tools that reach a person or another session, schedule or wake the job (its lifetime belongs to the daemon), or run commands outside the Bash guard's checks (`Monitor` runs its own command or opens a WebSocket): `CronCreate`, `CronDelete`, `CronList`, `ScheduleWakeup`, `RemoteTrigger`, `PushNotification`, `SendMessage`, `ListAgents`, `Monitor`, `Workflow`, `EnterWorktree`, `ExitWorktree`, `AskUserQuestion`, `ExitPlanMode`, `Artifact`, `ArtifactData`, `ArtifactComments`, `ArtifactCheck` (the guard's tool allowlist refuses these and every other tool not listed there; MCP tools only by their exact job-role names `mcp__agent-jobs__memory_search|memory_write|notify_owner|check_mark`, kept equal to the job-role registry by a test; the refusal of `Monitor` and `ScheduleWakeup` tells the job to wait with a foreground command or a bounded Bash loop). `WebFetch`/`WebSearch` denied unless kind = research.
- **Guard hook** (PreToolUse, matcher `*`; first a *tool allowlist* (`internal/guard/toolallow.go`): a job may call only Bash, Read, Write, Edit, MultiEdit, NotebookEdit, Glob, Grep, LS, TodoWrite, WebFetch/WebSearch (closed by the deny rules unless kind = research), Skill (the delivered skills), ToolSearch (loads deferred tool schemas), the in-session todo tools TaskCreate/TaskUpdate/TaskList/TaskGet, TaskOutput/BashOutput/TaskStop/KillShell for the job's own background shells (inside its scope), the subagent tool Agent/Task (under its cap) and the job-role MCP tools `mcp__agent-jobs__*`; every other tool, known or future, is refused with the reason; then it inspects Bash, the file tools Write/Edit/MultiEdit/NotebookEdit and the read tools Read/Grep/Glob/LS (see *state reads* below); for a file tool it rejects a `file_path`/`notebook_path` inside a `.git` directory – checked as given (made absolute against the hook's `cwd`, cleaned, case-insensitive `.git` segment, git config/hooks/`$GIT_DIR` paths) and with symlinks resolved on the longest existing prefix (a dangling link is followed by its target; a `..` in that target is walked as the kernel walks it, after the symlinks of the part before it, not dropped lexically, with at most 40 dangling links per resolution: `cfg -> jump/../hooks/pre-commit` with `jump -> .git/objects` reaches `.git/hooks/pre-commit`), so a link in the job dir pointing into `.git` is caught; a path with a `..` segment is rejected outright (the kernel resolves `link/..` after the symlink, while cleaning drops it lexically); paths inside the job worktree's real git dirs (admin dir and common dir, from `git rev-parse` at prepare time, passed to the guard as `--git-dir` – `settings.json` is written after the worktree exists) are rejected whatever they are named). Prefix deny rules miss spellings, so the guard *parses* each command: quotes removed, split on `;` `&&` `||` `|` `&` newlines and parentheses, comments and here-doc bodies skipped, env prefixes and wrappers (`env`, `command`, `exec`, `nohup`, `timeout`, `xargs`, `sudo`, …) stripped, `$(…)`/backticks/`<(…)`, `sh|bash|zsh -c '…'` and `eval` parsed as nested scripts. Around git/gh, a form it cannot resolve statically is rejected with «guard cannot verify this form; write it as a plain command» – git/gh inside `$(…)`, backticks, `<(…)`, an unquoted here-doc body, `eval` or `sh -c`; stdin redirect, here-doc or here-string into git/gh (commit messages go through `-m '…'`, `-m "$(cat <<'EOF' … EOF)"` or `-F <file>`; `-F -`/`/dev/stdin` rejected); a command name, git subcommand, gh subcommand, `-c` value or commit message from a variable/substitution; a glob/brace character (`{ [ ? *`) in any word that decides which program runs – the command name, wrapper names and their option values, the `timeout` duration (`{git,push}`, `/usr/bin/g[i]t`, `timeout {5,git} push`; leading keywords, shell assignments and `[`/`[[` exempt) – or in a git global option or subcommand or a gh subcommand; `eval`/`sh -c` of a variable; a shell reading commands from stdin (`… | sh`, `bash <<EOF`); `env -S`; `xargs git`; attached `-cKEY=V`, `-C.`, `--config-env`, `--exec-path`; `alias` mentioning git/gh; any non-reader program (`find -exec`, `flock`, `trap`, `python -c`, `node -e`, `npx`, …) with git/gh (also `git-<sub>`), a shell or an agent among its arguments – as a whole word, a path base name, or a word inside an argument (`python3 -c '…subprocess.run(["claude", …])'`, `node -e '…codex…'`, `npx @anthropic-ai/claude-code`, `node …/claude-code/cli.js`; words matched: `git`, `gh`, `sh`, `bash`, `zsh`, `dash`, `fish` bounded by characters other than letters, digits, `_`, `-` and a leading `.`; `claude`, `codex`, `gemini`, `aider`, `cursor-agent` also with a `-suffix` (`claude-code`, `gemini-cli`, `aider-chat`, `@google/gemini-cli`, `@openai/codex`)) (readers such as `echo`, `grep`, `cat`, `which` are exempt); `cp`/`mv`/`install`/`ln` with git, gh, `git-<sub>`, a shell or an agent as an argument (a renamed executable; also via `$(which git)`).   - git identity overrides that differ from config `git_name`/`git_email` (none configured → any override is rejected): `git config [--global|set] user|author|committer.name|email <value>`, `--author`, `GIT_AUTHOR_*`/`GIT_COMMITTER_*` (also `GIT_CONFIG_KEY_n`/`GIT_CONFIG_PARAMETERS`) even in a call without git. the protected dirs, their symlinked descendants followed, are scanned for that up to 16384 entries, past which a multiply linked target is refused), and for a recursive write (`chmod -R`, `cp -r` or `mv` into a directory, `rsync`, `tar -x -C`, `unzip -d`, the other tree writers) a hard link of a protected file anywhere in the destination tree, symlinks followed (scanned only while some protected file has another link, up to 16384 entries per call, past which the destination is refused); and a variable set in the hook's environment, which the job's shell inherits, is expanded like `$HOME` (`chmod u+w "$GIT_CONFIG_GLOBAL"`, `${GIT_CONFIG_VALUE_0}/pre-commit`, also `${VAR:-…}`). File tools also never write into the state dir outside the job's own folder (other jobs' files, `goals.md`, the archive: the same rule as for reads). Path resolution is linear in the word (each segment looked at once; a code word – inline code by the command's own option semantics (`python3 -c`, `perl -e`, `node --eval`, `php -r`, `bash -c` or `-ec`, the awk program), a here-doc or here-string – over 4 KB (PATH_MAX, no path the kernel opens) that holds several tokens is resolved by its tokens only; a plain operand or redirect target is always resolved as one whole path, since a program such as sqlite3 may normalise a longer name in userspace and open it), and the check has its own 5 s budget: past it the call is refused as too complex to verify, whatever the hook runner's timeout does. The whole decision (`guard.Decide`, every rule) has a 10 s deadline (`guard.DecideBudget`) past which the call is refused, since a hook that times out lets the tool run; the job's settings give the guard hook an explicit timeout of 30 s (`jobs.GuardHookTimeout`), symlink resolutions are memoized per decision, and a Bash command over 64 KB is refused before it is parsed. While a configured path (protected path, git dir, state dir, job folder) cannot be resolved within the symlink budget, every write is refused. Words are resolved by `internal/guard/pathres.go`: `~/`, `$HOME`, `${HOME}` and the variables set in the hook's environment expanded; relative words against the call's cwd and every directory a literal `cd`/`pushd` in the call leads to (also when that `cd` may fail); symlinks resolved component by component the way the kernel looks a path up (one `lstat` per component, a dangling link followed by its target text, a `..` in it taken after the links before it; past 40 links, the kernel's limit, which the kernel counts from the physical cwd and a tool such as `mkdir -p` restarts per component, or past 4096 components of link targets in one resolution, the call is refused as too complex to verify, file tools too); protected paths are resolved the same way and kept under both spellings, so one that does not exist yet (`config.json -> /outside/new.json`, a cards dir behind a symlinked parent) is protected where it would be created. After a `cd` the guard cannot resolve (`cd $X`, `cd $(…)`, `cd -`, `pushd +N`, a `CDPATH`), and for `~user/…`, a relative word whose segments could lead to a protected path from some directory (or contains `..`) is refused. Not resolved (residual gaps, DEVIATIONS #12): a path built at run time (a variable assigned in the call or not set in the hook's environment, `$(…)` or backticks, a file list `xargs` reads from a file, a program an interpreter reads from a file or from a pipe stage whose text the guard does not see, a descriptor opened by inline code or a program on a path the guard does not see, a path assembled or escaped inside inline code such as `'jobs'+'.db'`, `os.path.join(…)`, `\x2e`), a plain ancestor in free text or outside `$HOME` combined with a relative path at run time, a relative path inside inline code after a `cd` the guard cannot resolve (only whole words are matched by segments there), a symlink created at run time by something the guard does not recognise as link creation and used with `..` in the same call, a `cd` made in an earlier Bash call (relative words resolve against the cwd the hook reports and the `cd`s of the same call only), and a script the job writes and runs. A subagent runs inside the job's claude process, so its tool calls hit the same deny rules and guard, and it inherits the job marker.

A non-empty `--subagent-log` of any other shape refuses every tool call (fail closed: a misconfigured hook does not turn the rule off). The read tools: `Read` (`file_path`), `Grep` (`path`; recursive, so an ancestor of the state dir is refused too), `Glob` (`path` joined with the pattern: refused when a wildcard component at or above the state dir can stand for one of its components, e.g. `thr*/jobs/*/report.md` from `~/.agent-jobs`, when `**` sits at or above it, or when an existing match lies in the state). Bash: every word of every command (plain readers included: `cat`, `grep -a`, `head`, `tail`, `less`, `od`, `xxd`, `base64`, `strings`, `cp`, `sqlite3`, …), every path-like piece of a word or here-document (split on quotes, `=`, `:`, brackets, separators: inline code, option values, assignments), every input or output redirection (also a bare `< f` / `> f` without a command word), every directory a literal `cd`/`pushd` leads to, and a word with glob characters as a pattern (same test as the Glob tool, plus every existing match `filepath.Glob` finds, also through a symlink). Recursive readers – `grep -r`/`-R`, `-d recurse`, `--directories[=]recurse`, abbreviated `--recursive`/`--dereference-recursive`/`--directories`; `rg`, `ag`, `ack`, `zip`, `tar`, `rsync`, `tree`, `cp -r`/`-a`, `ls -R`, and `find` in any form (it lists every name and feeds `-exec`) – are refused on an ancestor of the state dir, also when that is their working directory (`cd ~ && rg x`); so is every stage of a pipeline that feeds `xargs` (`find ~ | xargs cat`, `echo ~/.agent-jobs | xargs ls`). Working directory: each command of the top-level script resolves relative words against the call's directory and the literal `cd`/`pushd` targets *before* it (`cat ../prompt.md; cd ..` is allowed); when the text order is not the execution order (a loop, a function, `eval`, `source`, `trap`, `alias`) and inside nested scripts every directory of the call counts. A command's own working-directory option is resolved too: `env -C|--chdir`, `sudo -D|--chdir`, `git -C` (global options, cumulative), `-C`/`--directory` of `make`, `tar`, `go`, `ninja`, `meson`, `pnpm`, and `--chdir`, `--cwd`, `--prefix`, `--dir`, `--working-directory`, `--workdir`, `--wd` of any program; such a directory inside the state is refused like a `cd`, and one from an expansion, or `chroot`, is refused (not modelled). Symlinks and `..`: paths resolve as for protected paths (homes, cd chains, symlinks on the longest existing prefix), and a path with `..` is also resolved the way the kernel does – component by component, a symlink replaced by its target before the `..` applies (`up/../k/…` with `up -> <own>` reaches `jobs/k`); a `..` after a component that does not exist yet (it may be a symlink the call creates), or after a wildcard, is refused; `cd -P` is covered by adding the kernel's directory next to the lexical one. `ln -s` / `cp -s` targets are resolved against the link's directory and refused when they lead into the state outside the job's folder or to the state dir or an ancestor of it (`ln -s ~/.agent-jobs A`); in a call that creates a symlink any other word with `..` is refused (`ln -s .. L; cat L/../k/…`, also after replacing an existing directory by a link). The Write tool cannot create a symlink. After a `cd` the guard cannot resolve, a relative word naming the state dir or one of its entries (`jobs.db`, `jobs/…`, `archive`) or containing `..` is refused. The job's own folder stays readable (prompt, report, work). Known false positives (refused, by design): `mkdir d && cd d && cmake ..` in one call (`d` does not exist when the guard looks; split the call), `find ~ …`, `ls -R ~`, a link to the state dir or `~`. **Limits.** This is a defence-in-depth layer in a shell-parsing guard, not a sandbox: it sees the spellings it parses, not what programs do at run time. Not covered: paths built at run time (variables other than `$HOME`, substitutions, file lists read from a file by `xargs -a` or a loop), symlinks created by other programs inside the same call (`tar x`, `unzip`, `git checkout`, `python -c os.symlink(…)`) followed by a path without `..`, a program that reads directories it is not given (a config file, a build tool), and scripts the job writes. Read isolation at the kernel level (a mount namespace or Landlock rule that hides `<state>` except the job's folder) is the separate future item that closes these.
  Unparsable hook input fails closed.
- **Fork subagents off** (wrapper, claude jobs only): every inherited `CLAUDE_CODE_FORK_SUBAGENT` is dropped and `CLAUDE_CODE_FORK_SUBAGENT=0` is set on claude (fork subagents are on by default in `claude -p` since the 2026-10-16 release; owner decision 2026-10-18, `docs/DECISIONS.md`); ordinary subagents and their per-job cap are unaffected; a codex job gets the environment unchanged.
- **Job marker** (wrapper, before claude starts): any inherited `AGENT_JOBS_JOB` is dropped and `AGENT_JOBS_JOB=<job id>` is set on claude, so every process of the job carries it (also the marker doctor procs will use). Under the marker the binary refuses every command except `mcp --role job`, `guard`, `run-wrapper` and help (start, cancel, status, list, result, tick, daemon, init, `mcp --role orchestrator`, …: «refused: running inside job»), and `mcp.Serve` refuses the orchestrator role on its own. The marker is an environment variable, so a job *can* remove it in a script it writes (the guard is not a sandbox); the guard rejects the direct spellings (`unset`, `env -u`, assignments, `mapfile`). Two process-based checks therefore back it up for the same control commands: (1) the ppid chain is walked through `/proc` (at most 256 steps) and the command is refused if an ancestor's argv is the wrapper's (`<bin> run-wrapper <jobdir> --token …`, matched by structure, or an `agent-jobs*` script run by an interpreter); (2) the command is refused if its session leader (`getsid(0)`, read from `/proc/<sid>/cmdline`) has the wrapper's argv shape: the wrapper starts with setsid, so it leads the session of every job process that did not call setsid itself – also of an orphan re-parented away from the wrapper – and this check does not depend on the agent or state dir the command targets; (3) as a fallback when the leader has exited, once the agent's store is open, the command is refused if its session id equals the recorded pgid of one of that agent's running jobs. Checks (1) and (2) are Linux-only and **fail open** when `/proc` cannot be read (and on macOS, where they are skipped; the marker and check (3) still apply). Before them, (0) the command is refused when `/proc/self/cgroup` names a job scope (`agent-jobs-*.scope`, any hierarchy line, any path component – also a sub-cgroup a job made inside its scope); this check also fails open when the file cannot be read. Without a scope (fallback), a job process that both drops the marker and calls `setsid` and has left the wrapper's process tree is not caught – the guard rejects the direct spellings of that as well, but a script the job writes is not inspected; with a scope it is refused by (0). Together these reject the direct spellings by which a job could start, cancel or manage jobs; not a sandbox (a script the job writes is not inspected, and without a scope a `setsid` + re-parented process that dropped the marker is not caught).
- **Session sweep** (wrapper, after claude exits, before `exit_code`): it ends what the job left in its session (and, with a scope, in its cgroup), so the processes a job started in the ordinary way do not outlive it. Processes a daemon outside the job starts for it (cron, tmux, …) are not in the session or the scope; the guard rejects the direct spellings of those (see «Cgroup containment»). The wrapper leads its own session (setsid), so on Linux it lists every live process whose session id is the wrapper's (from `/proc/<pid>/stat`, zombies skipped, the wrapper itself excluded) – also processes in other process groups and orphans re-parented away from it – sends them SIGTERM, waits up to 3 s, sends SIGKILL to whatever is left, and repeats (at most 5 rounds) until the session is empty; the count goes to `stderr.log`. Every signal goes through a pidfd: the descriptor is opened first (`pidfd_open`), session membership is checked only after it is open, and the signal is sent through it (`pidfd_send_signal`), so a pid reused by an unrelated process is never signalled. Without pidfd support (ENOSYS) nothing is signalled; there is no fallback to a bare `kill(pid)`. Fail closed: if processes are still alive after the last round, or the session cannot be enumerated or signalled, the wrapper still writes `exit_code` but first writes `sweep_incomplete` (survivor pids, then the error), and the daemon fails the job with «processes survived the job»; the job-done line ends with the same words. The daemon opens the marker without following links or blocking and reads it only as a regular file. Residual gap: the `/proc` enumeration is not atomic, so a process that forks between the directory read and the child's stat can leave a child that round did not see (the next round sees it, and one that keeps outpacing the rounds ends up as a survivor, failing the job); a survivor can also tamper with the job dir before the daemon reads it. With a scope, the daemon's stop of the whole unit (atomic, by systemd) follows at collection. Only then is `exit_code` written, so a job is never reported finished while one of its processes can still act (e.g. a markerless orphan waiting for the session leader to go and then starting a job for another agent). This is also the reference's ghost-process cleanup for preview servers, browsers and wait loops a job forgot. Outside Linux the wrapper sends SIGTERM to its process group only (it ignores SIGTERM itself meanwhile); the sweep inside a judge's manifest-check step sends nothing there, so the step's catch of stop signals holds until the runner starts and the runner does not inherit SIGTERM ignored (the script ran in its own process group, ended with it). Without a scope, a process that called `setsid` itself has left the session and is not swept (DEVIATIONS #9, residual gaps); with a scope the cgroup sweep below reaches it.
- **Cgroup containment** (Linux with systemd; DEVIATIONS #14). Config `cgroup_scope` (env `AGENT_JOBS_CGROUP_SCOPE` wins): `auto` (default) launches every wrapper in its own transient user scope when a throwaway `systemd-run --user --scope … true` succeeds, else falls back with a log line – except on a host where a scope was created before (`<state>/scope-ok`): there a failing probe requeues the job every tick for up to 10 minutes (`scope-failing-since`) before falling back, so a bus hiccup does not silently weaken a job; `required` likewise requeues within that window and then refuses. The containment of every launched job is shown as `scope <unit>` or `session only` in `status`, `list`, MCP `job_status` and (`session only`, `stop pending`) on the job-done line. `scripts/install-linux.sh` runs `init --pin-scope`, which writes `cgroup_scope: required` into `config.json` when it is unset and a probe succeeds; `required` refuses a job that cannot get one («refused to start: cgroup_scope is required …»); `off` never uses one. When neither `XDG_RUNTIME_DIR` nor `DBUS_SESSION_BUS_ADDRESS` is set and `/run/user/<uid>/bus` exists, the daemon points `XDG_RUNTIME_DIR` there for its systemd calls. A cgroup is inherited by every descendant and survives `setsid`, double forks and re-parenting, so: (a) control commands refuse inside a job scope (check (0) above); (b) after claude exits the wrapper, if its own cgroup is the expected `agent-jobs-<agent>-<id>.scope` or a sub-cgroup below it, sweeps from the scope itself the scope's cgroup subtree (pids from every `cgroup.procs` under it, itself excluded) in the same pidfd rounds as the session sweep – membership re-checked through `/proc/<pid>/cgroup` after the pidfd is open, zombies skipped – then the session as well, and only then writes `exit_code` (survivors fail the job as above); (c) the daemon stops the whole unit on cancel, timeout and every collection (see «Scope stops»). The scope sits under the user manager's `app.slice`, not under `agent-jobs@<agent>.service`, so a daemon restart never touches it (tested with a real `KillMode=process` unit restart). What a scope does not close (same uid, not a sandbox): a process can write its pid into another cgroup's `cgroup.procs` under the user manager, or ask the user manager for a new unit over D-Bus. The wrapper therefore drops `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR` from the job's environment, and the guard rejects every command that starts processes outside the job's scope (owner decision 2026-10-17, `docs/DECISIONS.md`): `systemd-run`, `busctl`, `dbus-send`, `gdbus`, `qdbus`, `qdbus-qt5`, `qdbus6`, `dbus-run-session`, `crontab`, `at`, `batch`, `tmux`, `screen`, `pm2`, `docker`, `docker-compose`, `podman`, `podman-compose`, `ssh`, `machinectl`, `loginctl`, `unshare`, `nsenter` as commands (also behind wrappers and `xargs`) and where another program runs them: the value of an exec option (`find -exec`, `rsync -e`, `go test -exec`, `--rsh=`), a positional of a runner (`setsid`, `watch`, `flock`, …), a word inside code (an argument with spaces, quotes or parentheses: `python -c`, `node -e`, `awk`, `trap`), an absolute path or a substitution given to a copier; a package, directory, make target or test name merely named after one (`go test ./internal/ssh/...`, `make -C docker`) is data. `systemctl --user` (also abbreviated; `systemctl` behind `xargs` and in those positions too), and any write into the cgroup file system (redirection, or an argument of a program that is not a plain reader) in the spellings the guard resolves: paths are cleaned (`//`, `/./`, `x/..`), made absolute against the call's directory and symlink-resolved, and match on a `sys/fs/cgroup` segment run, a cgroup core file base name (`cgroup.procs`, `cgroup.threads`, `cgroup.subtree_control`, `cgroup.kill`, `cgroup.freeze`, `cgroup.type`, `cgroup.max.*`), or any path through `/proc/<pid>/root` or `/proc/<pid>/cwd`. `~` is expanded with HOME; every `cd`/`pushd`/`popd` of the call (also inside `sh -c` or a substitution, in any order) adds candidate directories against which relative targets are checked, and `cd`/`pushd` into `/sys`, `/sys/fs` or the cgroup file system, `ln` to `/`, `/sys` or `/sys/fs`, and a cd with `CDPATH` in the call are rejected. Fail closed: a redirection target or a writer's argument (tee, dd, cp, mv, install, ln, rsync, truncate, sed, mkdir, …) computed inside the call is rejected in any call – a command or process substitution, a variable the call sets (assignment, `read`, `mapfile`/`readarray`, `for`/`select`, `declare`/`export`/`local`/`typeset`/`readonly`, `printf -v`, `${X:=…}`, PWD after a cd), a positional, indirect or `$_` expansion, any variable after `.`/`source` or `declare -n`, and any write target after an `ln` with a variable argument; a plain environment variable (`"$OUT"`, `"${OUT}"`) is rejected only when the call mentions the cgroup file system or has a cd the guard cannot resolve (`cd -`, `cd "$X"`, a `popd` that is not the call's last command), as is `~user` and a relative target after such a cd; the mention also counts when the cgroup path is split by an expansion that may be empty (`/sy${N}s/fs/cg"$N"roup`, positionals) or spelled with ANSI-C quoting (`$'s'`; any `$'…'` with an escape counts as a mention), and a variable write target that names a cgroup core file once such expansions are dropped (`x/cgroup${N}.procs`) is rejected. A sed script (the first operand, `-e`/`--expression`) is not a write target unless it may hold a `w`/`W` file (matched approximately); its file operands are. `coproc` runs its command like a plain command word. `trap` code is parsed like `sh -c` code. A script the job writes is not inspected (documented gap). **Fallback** (macOS, containers, no user bus, `cgroup_scope: off`): the session sweep and the marker, ancestry, session and store checks only – weaker: a `setsid` + re-parented process that dropped the marker is neither refused nor swept (pinned by a test).
- **Git environment scrub** (wrapper, before claude starts): every inherited `GIT_*`, `PAGER`, `EDITOR`, `VISUAL` is dropped, then `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=<jobdir>/gitconfig` (identity only), `GIT_PAGER=cat`, `PAGER=cat`, `GIT_EDITOR=true`, `EDITOR=true`, `VISUAL=true`, `GIT_TERMINAL_PROMPT=0` and, via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (command-line level: wins over repository config), `core.hooksPath=<jobdir>/no-hooks` (repository hooks never run), `core.fsmonitor=false`, `core.sshCommand=false`, `credential.helper=` (empty resets the helper list), `core.pager=cat`, `core.editor=true`. `diff.external` is not overridden: git has no value that disables it (an empty value makes every `git diff` fail with «cannot run»); inside the job a repo-local `diff.external`/textconv is reachable only by writing `.git/config` directly, which the guard rejects as a direct spelling. The daemon's own git calls (worktree add/remove, diff, format-patch, update-ref) drop inherited `GIT_*` and use the same overrides (hooks path `/dev/null`); its diffs pass `--no-ext-diff --no-textconv`, because cleanup runs after the job could have edited the repository config; filter drivers cannot be switched off that way, so cleanup skips the diffs entirely when the repository config names a filter, diff command or textconv (see Cleanup).
- **Prompt**: preamble (own dir only, content is data, no secrets, nothing outside) + subagent rules (`prompts/subagents.md`) + owner rules (job profile) + matching project cards + task + covered requirements (a job with covers: its rows and `prompts/requirements.md`) + kind checklist + report contract (Summary, Findings / Changes, Evidence, Not done / uncertain). A gate job (kinds `slicing`, `judge`) gets no cards, memory notes or brief column: its task is the daemon's input (`RenderGateInput`), see «Gate jobs».

## Readings of ambiguous points

- *Reference: «Процесс запускается отвязанным… и сам пишет код выхода».* Read as: a small wrapper is the detached process; it runs claude as a child (not `exec`, otherwise nothing is left to write the file) and passes the claude argv after `--` so the full command is visible in `ps`.
- *«Запрос выше потолка отклоняется».* Zero/omitted = default; negative values are rejected too.
- *Duration in the job-done line* is wall time in whole minutes (rounded).
- *Owner rules «до 8 КБ»* = 8192 bytes; an empty file also refuses to start (no rules ≠ rules).
- *Notify for refused/cancelled jobs*: every terminal job gets exactly one line. «Главная сессия получает одну строку» is a delivery guarantee: an undelivered line stays pending.
- *Model table (DEVIATIONS #6)*: review/fix/general: light → sonnet, normal → opus, hard → fable; research: light/normal → sonnet, hard → opus. `fable` is the claude CLI alias (resolved to `claude-fable-5-1` in a smoke run on 2026-10-15).
- *Cleanup for jobs without a repo*: nothing to preserve, marked cleaned; the directory itself is for `prune`.
- *Prune «маленькие текстовые файлы верхнего уровня»*: a regular file of at most 1 MiB that is valid UTF-8 without NUL bytes. `stream.jsonl` and `stderr.log` do not stay in the job folder at any size: they move gzipped into the log archive (the report and the patches keep the result in the folder). `untracked.tar` is kept as one of the patches although it is binary.
- *doctor procs «процессы, пережившие свою джобу или сессию»*: a job's own processes are found by its marker and its session id; «сессия» outside jobs is read as a session whose leader is gone, narrowed to the reference's examples (preview servers, browsers, wait loops).
- *notify_owner «уведомление владельцу»*: through the agent's existing channel (DEVIATIONS #4): the orchestrator session receives a `[jobs:notify-owner]` line and relays it; undelivered rows of the last 24 h show in `agent-jobs status` (no id) and are a `system_doctor` problem (`undelivered_notifications`). They are not retried: the caller got the error.
- *system_doctor «хуки»*: the hooks a job depends on – the guard hook as written into settings.json, the owner rules a job needs to start, the notify target.
- *trash_move*: one rename on the same filesystem; a copy across filesystems would not be reversible deletion, so it is refused.

## Memory notes in the brief

*Reference: «Демон сам добавляет до шести ближайших заметок из общей памяти команды».* `Manager.prepare` calls `LookupMemoryNotes` before it writes `prompt.md`: one `brain.Search` with the job's title and brief (first 4000 bytes, cut on a rune boundary), limit 12, under `MemoryTimeout` (5 s; the search runs in its own goroutine, so even a brain that ignores the context cannot hold the job). `RenderMemoryNotes` places a «Memory notes» section after the project cards and before the task:

- notes found: path, scope and score per note, the snippet (≤ 800 bytes, control characters dropped) quoted line by line with `>`, so a note cannot open a heading of the brief; marked as data written by others;
- none found: one line saying so;
- error or timeout: «Shared memory was unreachable when this job was prepared (reason)»; the job starts anyway, the daemon logs the reason;
- notes written by jobs (`MarkJobNotes`: the path is in the store table `job_notes`, or the snippet carries the job's marker line) are left out; the first 6 of the rest are quoted and the section counts the left-out ones;
- after an unanswered lookup the next ones are skipped for `MemoryBreaker` (1 min) with «skipped: …» as the reason;
- no brain configured: no section at all (briefs as before).

## Heartbeat

*Reference: «демон сам решает, есть ли повод разбудить агента ради его собственных целей. Сначала дешёвая проверка на Go …, потом маленькая модель решает»; the model is Sonnet, not Haiku (DEVIATIONS #1).* Off by default (`heartbeat.enabled`). `internal/jobs/heartbeat.go`, `internal/store/heartbeats.go`.

- **Gate (Go, every daemon tick, after `Tick`).** In order, the first failing reason wins: off; goals file (`heartbeat.goals_file`, default `<state>/goals.md`) missing, empty or not a regular file (idle); a decision still pending; inside the local night window `[night_start_hour, night_end_hour)` (default 0-8, may cross midnight, start == end = none); less than `interval_minutes` (default 60) since the last wake, then since the last decision of any outcome (a `suppressed` one too: the model was called); `daily_max_wakes` (default 6) wake decisions already claimed this local day (counted from the store, so a restart keeps the cap); something pending for the session (a job-done line not delivered while a notify target is set, a missed-check alert pending, a `notify_owner` delivery in flight). Only the daemon's last gate result is stored (table `heartbeat_gate`, one row). A pending decision older than the call timeout + the tmux delivery timeout + 2 min is marked `abandoned` and never asked again; it still counts as the last decision.
- **Lock and claim.** `StartHeartbeat` runs at most one heartbeat per process in its own goroutine (the next ticks are not delayed; shutdown waits for it). `RunHeartbeat` first takes `<state>/heartbeat.lock` (flock, non-blocking: another process holding it = skip, recorded as the daemon's gate reason), then reads the clock and runs the gate, so a caller never acts on a gate evaluated before another heartbeat finished. `ClaimHeartbeat` inserts the `pending` row in one IMMEDIATE transaction that re-checks «no pending row», the interval since the last claim (daemon only) and the daily wake cap, so two daemons or a daemon and `run-now` never claim the same slot nor the same last wake of the day. The row exists before the model is asked.
- **Decision.** `claude -p --output-format json --model <heartbeat.model, default sonnet> --max-turns 1 --max-budget-usd <0.2> --tools "" --permission-mode default --settings <state>/heartbeat/settings.json --setting-sources project --mcp-config <state>/heartbeat/mcp.json --strict-mcp-config --no-session-persistence`, in the empty dir `<state>/heartbeat` (its `settings.json` denies every tool and turns hooks off; `mcp.json` lists no servers), the jobs' scrubbed environment (no brain token), its own session (setsid) and, like a job, its own systemd user scope when `cgroup_scope` gives one (`agent-jobs-<agent>-heartbeat-<n>.scope`; `required` without a scope = an error, no wake). Killed with its process group (and the scope stopped) at `timeout_seconds` (default 60). The prompt (stdin): the goals file (at most 8 KB, cut on a UTF-8 boundary, redacted, fenced as data), now, the last wake, and counts of running and queued jobs, failed or timed-out jobs since local midnight without a recorded `job_outcome` (the prompt says "N failed today without a recorded outcome"), owner replies pending and missed checks. Any recorded outcome means the failure has been handled and excludes it from this count. The answer must be exactly one JSON object with the keys `wake` (bool) and `reason` (one line, 1..200 characters); anything else (text around it, a code fence, an extra or missing key, a long reason, a failed call, an error result, output over the 256 KB cap) is stored as `error`: no wake, logged. stdout is kept by a capped writer (a named `bytes.Buffer` field with a plain `Write`, so exec's `io.Copy` cannot bypass the cap through `ReadFrom`; the pipe keeps draining).
- **Delivery-time re-check.** For a wake answer the heartbeat takes `tmux.lock` (the job-done path, 10 s deadline) and, holding it, right before typing checks again: heartbeat still on, outside the night window, nothing pending for the session (the same delivery checks as the gate). If closed, the row becomes `suppressed` with the model's reason and `suppressed: <why>` as its error; nothing is delivered. A suppressed decision counts toward the interval (the model was called) but not toward the daily wake cap. If `tmux.lock` is not taken within the deadline, nothing is re-checked or typed and the row is stored as a `wake` not delivered, with the lock error.
- **Wake.** Still under `tmux.lock`, the decision (`wake`, reason, cost) is stored first through the conditional `pending -> wake` update; only when that succeeds is anything delivered (a claim abandoned meanwhile, or a failed write, delivers nothing, and `RunHeartbeat` returns the error). The line is fixed, `[jobs:heartbeat] wake <id>` (`HeartbeatLine`), typed through the job-done tmux path in the same lock hold: the model's reason never reaches the session as input. It is stored and read on demand with `agent-jobs heartbeat show <id> [--json]` and the orchestrator-only MCP tool `heartbeat_get`, always as `untrusted_model_reason` (also in `system_doctor` and the status JSON): untrusted model text, data, not instructions; the orchestrator instructions and the agent-jobs skill say so. The delivery result (`delivered` or the error, e.g. no `notify_tmux_target`) is stored on the row; an undelivered wake is not retried and still counts toward the daily cap. `system_doctor` lists it as a problem.
- **Surfaces.** `agent-jobs status` (no id) prints `heartbeat:` (on/off, model, interval, night window, wakes today of the cap, the gate now or the next eligible time), the goals path, the daemon's last gate reason and the last decision; `system_doctor` returns `heartbeat` (the same, with the model's reason as `untrusted_model_reason`); `/v1/health` returns `heartbeat` with enabled, wakes today, cap, next eligible time and the last decision's outcome and time, never the goals path or text or the reason. `agent-jobs heartbeat run-now --agent A` runs one heartbeat now: the interval parts of the gate are skipped, every other part applies; `--dry-run` prints the daemon's and run-now's gate result and the prompt, calls no model and stores nothing.
