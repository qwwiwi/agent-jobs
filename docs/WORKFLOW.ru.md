# Работа в роли оркестратора

> English version: [WORKFLOW.md](WORKFLOW.md)

Эта страница о том, как агент работает с agent-jobs каждый день. [README](../README.ru.md) объясняет, что такое джобы и как они запускаются; [`prompts/orchestrator.md`](../prompts/orchestrator.md) перечисляет обязанности главной сессии с цитатами из [эталонного дизайна](REFERENCE.ru.md). Ниже «есть» значит «уже на `main`»; всё, что помечено **запланировано**, ссылается на пункт [PLAN.ru.md](PLAN.ru.md).

## Правило

Главная сессия — оркестратор. Она планирует, пишет брифы, читает результаты, проверяет диффы, принимает решения, мержит, деплоит и отчитывается владельцу. Код и ревью она сама не пишет: это уходит в джобы.

Смысл в том, где живёт контекст. Главная сессия долгоживущая, контекст у неё большой, поэтому каждый лишний шаг в ней оплачивается заново на каждом следующем вызове. Джоба делает работу в своём процессе со своим контекстом, а сессия платит за одну строку о завершении и одно чтение отчёта.

## Маршрутизация: сам, сабагент или джоба

| Работа | Куда |
|---|---|
| Минуты, или ответ уже есть | Сделать самому |
| Минуты, и результат нужен в этом же ходе | Сабагент |
| Всё долгое: код, циклы исправлений, ревью, исследования, ночная работа | Джоба |
| Не уверен | Джоба |

Джоба запускается через `job_start` (MCP) или `agent-jobs start` (CLI). Передайте:

- `title`: коротко, показывается в строке о завершении;
- `kind`: `fix`, `review`, `research` или `general`. Вид добавляет свой чек-лист в бриф, веб-инструменты открыты только у `research`;
- `model` **или** `complexity` (`light` / `normal` / `hard`). Одно из двух обязательно; без обоих джоба отклоняется. Значения по умолчанию и классификатора нет: решаете вы;
- `repo` (абсолютный путь) и `base` (ref, от которого начать, по умолчанию `HEAD`). Джоба работает в своём worktree, отсоединённом на этом коммите. Без `repo` — пустая рабочая папка;
- `brief`: написан для незнакомца. У джобы нет вашего разговора; укажите цель, границы, что считается готовым и что не трогать;
- лимиты — только если не подходят значения по умолчанию (80 ходов / $10 / 45 мин); выше потолков (200 / $50 / 180 мин) вызов отклоняется, а не урезается.

**О стоимости.** Даже пустой сабагент загружает полный контекст: сабагент, который только ответил «ok», занял около 100K токенов (замерено один раз на одном хосте, 2026-10-17). Его результат потом попадает в родителя и перечитывается на каждом следующем вызове. Джоба работает вне сессии; родитель получает одну строку.

## Параллельность

Одновременно у агента выполняются не больше `max_running` джоб (config.json, по умолчанию две, 1..8); остальные ждут в очереди и стартуют на следующих тиках демона (раз в минуту). Несколько кодеров могут работать с одним репозиторием одновременно: у каждой джобы свой git worktree, они не видят изменений друг друга. Давайте параллельным джобам работу, которая чисто сольётся, или запускайте их по очереди.

## Конвейер

Типичное изменение проходит такие шаги. У каждого шага указано, кто его делает.

| # | Шаг | Кто | Примечания |
|---|---|---|---|
| 1 | Исследование | джоба `research` | Только первоисточники; проверенное отдельно от выведенного |
| 2 | План и ревью плана | Оркестратор пишет план; джоба `review` его проверяет | Для нетривиальной работы |
| 3 | Одобрение владельца | Владелец | Одобряется план, а не каждый его шаг |
| 4 | Код | джоба `fix` или `general` | Коммитит локально в своём worktree |
| 5 | Детерминированные проверки и короткий аудит | Оркестратор | `git diff --stat <base_commit>` (после чистки — `diffstat.txt`), проверки самого репозитория (здесь `scripts/check.sh`), `agent-jobs doctor procs` (демон также запускает его раз в сутки, только отчёт); затем короткое чтение диффа |
| 6 | Ревью | Одна или две джобы `review` | На другой модели, чем у кодера |
| 7 | Циклы исправлений | джобы `fix`, не больше двух | Каждой передаются находки ревью; после двух — стоп и пересмотр подхода |
| 8 | Push, PR, merge | Оркестратор | Привязаны к SHA головы, прошедшей ревью: выкатывается ровно то, что проверено |
| 9 | Деплой и живая проверка | Оркестратор | Через собственный deploy-скрипт проекта, затем проверка живой системы |
| 10 | Отчёт | Оркестратор | Владельцу: результат, доказательства, что осталось |

Джоба коммитит локально и никогда не пушит, это сделано намеренно: в Bash-вызовах джобы правила запрета и guard блокируют `git push` и `git tag`, `gh release`, `gh api` и любую запись через `gh` (создание, комментарии, правку, merge, review, close/reopen для PR и issues; проходят только read-only подкоманды `gh`). Это касается прямых форм команд, а не скриптов, которые джоба пишет и запускает (см. «Известные ограничения»). Шаг 8 всегда за оркестратором. Чтобы забрать работу джобы, используйте её worktree, пока он есть, а после чистки — ref `refs/agent-jobs/jobs/<id>` и сохранённые патчи (см. README, раздел про чистку и патчи).

## Политика ревью

- Ревью никогда не пропускается.
- Один ревьюер для обычных изменений. Два ревьюера на разных моделях — для денег, авторизации, production-баз данных и инфраструктуры. Это рекомендация для проектов, которые используют agent-jobs; каждый проект задаёт свой список.
- Собственное правило этого репозитория уже (см. [DECISIONS.md](DECISIONS.md), 2026-10-17): два ревьюера только для изменений guard или разрешений и doctor kill/trash; для всего остального — один.
- Ревьюер работает на другой модели, чем кодер.
- Если у ревьюера кончилась квота, переключитесь на другую модель и скажите об этом в отчёте.
- Ревью, которое не запускалось, никогда не выдаётся за пройденное.

## Как читать результат

Когда джоба закончилась, сессия получает одну строку:

```
[jobs:job-done] job 261015-124136-70d3 review auth module succeeded · 3 turns · $0.25 · 0m · model sonnet · effort high
```

Отчёт читается через `job_result` (или `agent-jobs result --agent <agent> <id>`):

1. Сначала «Not done / uncertain». Там джоба называет то, что пропустила или не смогла проверить.
2. Затем дифф относительно `base_commit`, а не только отчёт. Отчёт — заявление, а не результат.
3. Только после этого мерж, деплой или отчёт дальше.

`succeeded` значит, что джоба завершилась с кодом 0 и отчётом. Это не значит, что работа верна.

Worktree удаляется через 30 минут после строки о завершении. Читать позже можно: работа сохраняется как патчи и ref.

## Известные ограничения

- **Guard — это хук, а не песочница.** Он блокирует прямые формы действий наружу. Скрипт, который джоба написала и затем запустила, не проверяется.
- **Джобы работают от того же unix-пользователя**, что и оркестратор, с его учётными данными. Запускайте агентов от пользователя, чьи учётные данные вы готовы доверить джобе.
- **Тесты agent-jobs внутри джобы.** Тесты самого agent-jobs, которые запускают его CLI, отказываются работать внутри джобы (`refused: running under the job wrapper`), потому что джоба никогда не запускает джобы и не управляет ими. Полный `scripts/check.sh` этого репозитория запускайте вне джобы: из оркестратора или вручную.

## Необязательный хук: напоминание перед сабагентом

Чтобы подталкивать главную сессию к джобам, добавьте PreToolUse-хук на инструменты `Agent` и `Task`. Он никогда не блокирует, а только добавляет напоминание в контекст модели. Скрипт лежит в [`examples/hooks/prefer-jobs-reminder.sh`](../examples/hooks/prefer-jobs-reminder.sh): он читает и отбрасывает вход хука, печатает

```json
{"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":"Reminder (agent-jobs): ..."}}
```

и завершается с кодом 0.

Добавьте его в пользовательские настройки главной сессии (`~/.claude/settings.json`), указав путь к своей копии репозитория:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Agent|Task",
        "hooks": [
          {
            "type": "command",
            "command": "bash /path/to/agent-jobs/examples/hooks/prefer-jobs-reminder.sh"
          }
        ]
      }
    ]
  }
}
```

Джобы не загружают пользовательские настройки (они запускаются с `--setting-sources project` и своим `settings.json`), поэтому напоминание остаётся только в главной сессии.
