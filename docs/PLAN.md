Same names as the reference, backed by the team's shared memory and task service (DEVIATIONS #2, #3). Jobs get `memory_search` and `memory_write` only.
- **Memory notes in the brief.** *Status: built in v0.3.0 ([PR #13](https://github.com/qwwiwi/agent-jobs/pull/13)); `internal/jobs/memory.go`.* The daemon adds up to six of the closest notes from shared memory to every brief, so a job does not rediscover what is already written down. ## Wave B

- **Resume.** `job_resume` and `agent-jobs resume <id>`: a new job with the same brief, the old commits and diff carried over from the saved patches, and a note at the top of the brief saying what was carried and what was not. *Superseded by E2* (built): resume continues the same job id and session; the carry-over survives as its fallback (fresh session in the worktree restored from the ref and patches, with a summary of the previous attempt).
- **Schedules.** `schedule_add`, `schedule_list`, `schedule_remove`. A cron expression in local time plus a prompt, checked every minute, delivered one of two ways:
  - into the live session as a tagged message (several due at once arrive as one message: «these are different instructions, do each one»);
  - as a job, when the schedule has a kind; the session then only sees the job-done line.
  Schedules store their model and limits at creation. A missed firing is lost, not queued, so check windows overlap. Schedule rows never expire; they are edited in place and deleted only by the owner.
  *Status: built, released in 0.4.0; `internal/jobs/cron.go`, `internal/jobs/schedule.go`, `internal/store/schedules.go`, `internal/mcp/tools_schedules.go`.* Orchestrator tools `schedule_add`, `schedule_list`, `schedule_set` (cron, prompt, enabled; edited in place) and `schedule_remove` (only on the owner's instruction); `agent-jobs schedules [--json]` lists them. A 5-field cron (ranges, steps, lists, month and weekday names, macros; the classic day-of-month / day-of-week rule) in local time, own parser, no dependency; checked in every daemon tick. Prompt one line, ≤ 2000 characters, control and bidi characters refused, `[jobs:` defanged. Session delivery: one line `[jobs:schedule] …`, several due in the same minute as one numbered line; with a kind a job is queued with the model, runner and limits resolved and stored at creation (validated like `job_start`, codex rules included). Each firing is claimed in the store first (`last_fired_at`): never twice for a minute (restart-safe; a local wall-clock watermark: the repeated hour at the end of DST fires each wall-clock minute once), a missed minute or a failed delivery is lost, never replayed.
- **Dead-man's switch.** Checks that stay silent when all is well leave a completion mark; a watchdog compares the marks with the schedule.
  *Status: built, released in 0.4.0; `internal/jobs/checks.go`, `internal/store/checks.go`, `internal/mcp/tools_checks.go`.* A check is a name (slug, ≤ 64), a 5-field cron in local time (the schedules' parser) saying when it must have reported, and a grace (default 60 minutes, 1..10080). Whatever stays silent while healthy leaves a mark: `check_mark` (orchestrator and job role, a job through the daemon's proxy) or `agent-jobs check mark NAME [--note T]`; a mark stores the time and an optional one-line note (≤ 300 characters, control and bidi characters refused, `[jobs:` defanged). Orchestrator tools `check_add`, `check_set` (cron, grace, enabled; in place), `check_list` and `check_remove` (only on the owner's instruction); `agent-jobs checks [--json]` lists them. The watchdog runs in every daemon tick and judges every expected time E whose E+grace has passed since the last judged one, oldest first (at most 1000 per check and tick). A mark belongs to exactly one E, a pure function of its time, the cron, the grace and the arm time: the earliest E after the arm time with E+grace ≥ the mark; E is missed when no mark belongs to it (no consumption state: insertion order and downtime do not matter; marks before the arm time never count; a window stores at most 20 marks, a mark is pruned only once its E is judged). Each judged E moves the evaluation watermark (the schedules' rule: absolute time and local wall-clock minute; conditional on the check's revision), so it is judged once, across restarts and daemons; each missed one is its own alert row with its own attempts, typed as one line per tick `[jobs:check-missed] <name> expected <E> (no mark within <grace>m)` or `<name>: N missed, latest <E> (…)` on the bounded session path, outside the lifecycle lock, fenced by an attempt token re-checked under `tmux.lock`, retried up to 5 times, at-least-once; failed alerts stay visible until a `check_set` acknowledges them. Expected times before the check was added, or re-armed by `check_set`, never alert; a skipped DST minute is not expected, a repeated one once. Missed checks (a late mark keeps them missed) and pending or failed alerts show in `agent-jobs status` and `system_doctor`.
- **Intentions.** *Status: built, released in 0.4.0; `internal/store/intentions.go`, `internal/jobs/intentions.go`, `internal/mcp/tools_intentions.go`.* `intention_add`, `intention_list`, `intention_set`: the agent's own goals, a table `intentions` in the agent's store (text one line, ≤ 500 characters; optional due date and priority; status `open` / `done` / `dropped`, edited in place, never deleted). Orchestrator only; `agent-jobs intentions [--status] [--json]` lists them.
- **`notify_owner`.** A message to the owner through the agent's existing channel (DEVIATIONS #4). *Status: built, released in 0.4.0; `internal/store/notifications.go`, `internal/jobs/notifyowner.go`, `internal/mcp/tools_notify.go`.* Orchestrator and job role (a job through the daemon's proxy); one line `[jobs:notify-owner] …` typed into the orchestrator session on the job-done tmux path, which relays it; agent-jobs calls no messaging API. Text one line, ≤ 300 characters, tags inside it defanged; urgency normal / high; per job ≤ 3 and ≤ 1 a minute, per agent ≤ 20 an hour; every call stored in `owner_notifications`, undelivered ones in `agent-jobs status` and `system_doctor`; CLI `agent-jobs notify-owner`.
- **Daily automation.** `prune` and `doctor procs` run once a day on their own. **Built, released in 0.4.0:** inside the daemon loop, once per local day at the first tick after `daily_hour` (default 4; `daily_off` disables); prune for real with the log archive, doctor procs report only (killing stays manual, `--kill`); the claimed day is stored (`daily` table), so a restart never repeats it and a missed day runs once, never caught up; each step time-boxed (10 min), in a goroutine that never overlaps itself or delays the ticks; the last run shows in `agent-jobs status` (no id) and `system_doctor`.
- **Codex runner.** *Status: built, released in 0.4.0; `internal/jobs/codex.go`.* A job can run on `codex exec` instead of `claude -p` (DEVIATIONS #5); without turn or budget caps there, so the timeout is the limit. Selected by a `gpt-*` model or `runner: codex`; read-only sandbox for review/research; write jobs refused unless `codex_write_allowed`; no guard inside codex (known limit); resume refused for now.

## Wave D

Approved by the owner on 2026-10-17 as part of the full mandate (see [DECISIONS.md](DECISIONS.md)); built after Wave C:

- **Heartbeat.** The daemon decides whether to wake the agent for its own goals: a cheap Go check (time, daily limit, night), then a small model decides (DEVIATIONS #1). *Status: built, released in 0.4.0, off by default (`heartbeat.enabled`); `internal/jobs/heartbeat.go`, `internal/store/heartbeats.go`.* Each tick a Go gate (enabled, goals file present, not inside the night window, `interval_minutes` since the last wake and the last decision, wakes today below `daily_max_wakes`, no decision running, nothing pending for the session); then one `claude -p` call (Sonnet, no tools, one turn, `max_budget_usd` 0.2, 60 s) answers `{"wake": bool, "reason": "..."}`, validated strictly; a wake is the fixed line `[jobs:heartbeat] wake <id>` through the job-done tmux path (the model's reason is stored, read with `heartbeat show` / `heartbeat_get`, never typed into the session). Table `heartbeats` (claimed before the call, so a restart never repeats it); `agent-jobs heartbeat run-now [--dry-run]`; `status`, `system_doctor` and `/v1/health` show it.
- **«Owner waits» Stop hook.** A job started at the owner's request is marked; until the orchestrator has written to the owner, a Stop hook does not let the session end its turn silently. *Status: built, released in 0.4.0; `internal/jobs/ownerwaits.go`, `internal/store/ownerwaits.go`, `internal/mcp/tools_ownerwaits.go`.* `job_start` `owner_waits` / `agent-jobs start --owner-waits` (store column `owner_waits`); the job-done line ends with `· owner waits`, and the finished job records «owner reply pending» before that line is delivered (table `owner_pending`, marked delivered in the same transaction as `notified_at`); `agent-jobs hook bind --agent A` (SessionStart) binds the orchestrator session, and `agent-jobs hook stop --agent A`, its Stop hook, blocks only that session, once per turn while a record is pending (never with `stop_hook_active`, fails open, also on incomplete input); the orchestrator tool `owner_replied` (job id or all) clears it; a record expires after `owner_waits_max_hours` (default 6); `agent-jobs status` and `system_doctor` show pending ones.
- **Read-only HTTP API** for a jobs dashboard (DEVIATIONS #8). *Status: built, released in 0.4.0; `internal/httpapi`.* Off by default (`http_api.enabled`), loopback or unix socket only, bearer token `<state>/http-api.token` (`agent-jobs http-api token --rotate`) on every endpoint; GET only: `/v1/health`, `/v1/jobs`, `/v1/jobs/{id}` (`?report=1`, 64 KB cap), `/v1/stats`, `/v1/schedules`; no briefs, prompts, env, config or paths outside the agent state; server timeouts, 8 KB headers, 10 requests/s per client.
- **Acceptance from a clean clone.** The whole install and a test job are replayed from a fresh clone before a release. *Status: built, released in 0.4.0; `scripts/acceptance-clean-clone.sh`, README «Release checklist».*
- **Wave D items 23-27:** risky-first review, a Progress section in reports, a job size check, secret redaction in reports and logs, an `acceptance_cmd` a job must pass.
  - *Status of risky-first review and `acceptance_cmd`: built, released in 0.4.0.* The review checklist (`prompts/kind-review.md`) lists the risky areas first, answers delivered / design / code separately and ends Findings / Changes with the subsections `### Blocking` and `### Non-blocking`, the verdict BLOCK if and only if Blocking is not empty. `acceptance_cmd` (`job_start`, `schedule_add`, `--acceptance-cmd`; not for review/research): run by the wrapper in the worktree after a clean exit 0, in the job's containment, scrubbed env, no guard, `acceptance_timeout_minutes` (15, max 60), 64 KB `acceptance.log`; a failure fails the job with `acceptance failed (exit N)` (HTTP API `acceptance_failed`); see ARCHITECTURE «Acceptance command».
  - **Secret redaction.** *Status: built, released in 0.4.0; `internal/jobs/redact.go`.* Known token formats (Anthropic, OpenAI, GitHub, Slack, AWS, Google, Telegram bot, JWT, PEM private keys, `Bearer`, generic `token|secret|password|passwd|api_key = <16+ chars>`) become `[redacted:<kind>]` in `report.md` (in place when the job ends; `keep_raw_reports: true` keeps a 0600 `report.raw.md`), the job-done line, `job_result` and `agent-jobs result`, the stats row and the previous-attempt excerpts of a resumed brief. RE2 only, scan capped at 4 MiB.
  - **Progress section.** *Status: built, released in 0.4.0; `prompts/report-contract.md`, `internal/jobs/report.go`.* The report contract asks for `## Progress` (one timestamped line per step) after «Not done / uncertain»; `job_result` returns `not_done` and `progress`, `agent-jobs result` prints those two sections first. A missing section is not an error.
  - **Job size check.** *Status: built, released in 0.4.0; `internal/jobs/briefsize.go`.* `job_start` (and schedules with a kind) refuse a brief above `max_brief_bytes` (default 32 KB); `size_warning` in the `job_start` result when the brief names more than `brief_warn_files` files (default 40) or has more than `brief_warn_headings` `## ` headings (default 8).

## Wave E: borrowed ideas (planned; E2 approved and built)

Each item waits for a separate owner go (E2 has it, see [DECISIONS.md](DECISIONS.md)); it is not part of the current mandate (see [DECISIONS.md](DECISIONS.md)). Items that diverge from the reference have a «proposed, not approved» entry in [DEVIATIONS.md](DEVIATIONS.md#proposed-not-approved-wave-e). Sources are open-source projects from the 2026-10-17 market scan. The Codex runner and schedules, also seen in those projects, are already in Wave B; Wave E does not change them.

- **E1. Subscription limit: wait for the reset and resume.** Keep the last rate-limit event; hold new launches when the window is near its limit; on a usage-limit error wait for the reset + 60 s + jitter and resume the same session (needs E2). Why: subscription windows, not dollar budgets, stop overnight jobs; `--max-budget-usd` is a client-side estimate, not a subscription cap. Source: arbab. Related: Wave D API-credit fallback (E1 waits, the fallback pays). Priority: high. DEVIATIONS E1.
- **E2. True session resume.** Assign `--session-id` before launch and drop `--no-session-persistence`, so `job_resume` continues the same claude session instead of starting a fresh job from the saved patches. Why: a timed-out or killed job keeps its context, including turns that produced no commit. Source: agent-dispatch. Related: Wave B Resume (patch carry-over stays as the fallback). Priority: high. **Status: approved by the owner as a priority and built in v0.3.0 (stop, resume, amend; see Done); DEVIATIONS #15.**
- **E3. Structured outcome.** Next to `report.md`, a machine-readable outcome (via `--json-schema`): status `done | partial | blocked`, changed files, checks with their exit codes, a not-verified list. Why: the orchestrator can triage without reading the report, and a job cannot claim a pass the outcome does not show. Source: arbab (fixed report schema), agent-dispatch (`STATUS: done|partial|blocked`). Related: the report contract (Done, PR #1); Wave D Progress section. Priority: high. DEVIATIONS E3.
- **E4. Verify by exit codes.** Check results are taken from tool exit codes in `stream.jsonl`, never from the model's summary; optionally a separate read-only verify job (no edit tools) runs the checks after a fix. Why: a report is a claim; exit codes are evidence. Source: arbab (verify / probe role). Related: Wave D `acceptance_cmd`. Priority: medium-high. DEVIATIONS E4.
- **E5. Claude Code native sandbox on top of the guard hook.** No network, no writes to `.git`, enforced by the OS rather than by command parsing (arbab: sandbox with `failIfUnavailable`, `dontAsk` plus an allowlist). Starts as a research spike on Linux (bubblewrap): what works under `claude -p` and what breaks (worktree git dirs, the job store, MCP). Why: the docs say the guard is not a sandbox (DEVIATIONS #9, #12); this would close part of that gap. Source: arbab. Related: Wave A cgroup containment, the guard. Priority: medium. DEVIATIONS E5 (only if adopted).
- **E6. `job_wait` / `job_peek`, an error taxonomy, flag-like input rejection.** `job_wait(timeout)` blocks until a job ends; `job_peek` returns a short progress tail; a failed job carries a cause (`budget`, `usage_limit`, `timeout`, `guard_refused`, `died`); MCP string inputs starting with `-` are refused. Why: a result within the same turn without Bash sleep loops; triage without opening logs; no CLI flag injection. Source: agent-dispatch, ai-cli-mcp (claude-async for exit causes). Related: PR #7 MCP job tools. Priority: low-medium. DEVIATIONS E6.
- **E7. Skills for jobs: a catalog and an explicit per-job selection.** Owner request, refined.
  - *Status: job-side part built, released in 0.4.0 (owner approved 2026-10-18, see [DECISIONS.md](DECISIONS.md); deviation recorded as [DEVIATIONS #16](DEVIATIONS.md)); `internal/skills`, `internal/jobs/skills.go`, `internal/jobs/skillrating.go`, `internal/mcp/tools_skills.go`.* Config `skill_roots` (each root holds `index.json`; missing or invalid = warning), `skills_max_per_job` (6, max 8), `skills_max_kb` (400). `job_start` `skills` / `start --skills` / `schedule_add` `skills`: defaults = `core` skills of the job kind plus the repository's project skills, `+name` / `-name` edits, unknown or deprecated names and budget overruns refuse the start; stored on the job. A whole brief line `skills: none` opts out of catalog skills (case-insensitive, whitespace allowed), matching external orchestrator hooks; nonempty `skills` edits conflict with that signal. An empty edits array keeps defaults. The shared config loader reloads skill roots and limits before MCP calls and daemon ticks (restart-only fields are logged; failed loads keep the last good config). Delivery is a symlink `<work>/.claude/skills/<name>` -> the catalog directory for the run only (owner: no copies), hidden by `info/exclude`, write-protected by deny rules and the guard, removed when the attempt ends; the repository's own skill wins; codex jobs get none. `skill_list` (with a local content search), `agent-jobs skills list|search`, `GET /v1/skills` and `stats --by skill --by-repo` (delivered vs used). Built differently from the design below: the catalog roots are read directly (no `agent-jobs skills index` command, no `scope` front matter, no lint step), and delivery links instead of copying. Not built: the pre-launch skill hook and `skills_decision` (a separate item), the weekly staleness digest, `/skill-doctor` and `claude plugin eval`.
  - Today: `--setting-sources project` means user-level skills (`~/.claude/skills`, plugins) are not loaded; a job sees only the target repo's `.claude/skills` plus the profile and project cards. Skills tend to be scattered across hosts and agents, with many duplicates and plugin copies.
  - Catalog: one registry built by `agent-jobs skills index` from front matter in each `SKILL.md` (name, scope `common | project:<repo> | agent:<name> | kind:<code|review|research>`, path, size, has scripts, network/secrets risk, owner, version/sha, origin); duplicate names resolved by an explicit priority order; a lint step in `scripts/check.sh`.
  - Where skills live is up to you: keep them locally on the host, use a shared skills catalog repo across your projects, or use project skills in the repo's own `.claude/skills`. The index reads the roots you configure; agent-jobs ships no catalog and prescribes no source. Each entry records its origin (root, plugin name and version).
  - Discovery and selection: MCP tool `skill_list(scope?, kind?, repo?)`. Defaults (the `core` skills for the job kind plus the project card's skills) are attached automatically; `job_start(skills=[...])` only adds or excludes (`+name`, `-name`); an unknown name refuses the start. Deterministic matching by kind and project first, hard budget of 5-8 skills per job; semantic retrieval only if matching proves insufficient.
  - Pre-launch skill hook: a PreToolUse hook in the orchestrator session on `job_start`, installed by the agent-jobs skill installer. Without `skills_decision` it denies once with up to about 8 candidates (status and a one-line description each); the orchestrator re-calls with `skills=[...]` or `skills_decision='defaults'`. No model call in the hook (the classifier was rejected, see DECISIONS). One extra round trip per job; deprecated/draft names refused unless explicit; the decision is stored in job metadata.
  - Lifecycle: `status: core | active | draft | deprecated`, `owner`, `last_verified`. deprecated is never loaded; draft only on explicit request. Staleness: not used for 60 days or not verified for 90 days goes to a review list; a weekly digest to the orchestrator.
  - Stats: skills used (Skill tool calls in the job's session log) and the job outcome go to SQLite; `agent-jobs skills stats` shows uses, success rate, last used, and feeds the sort order of `skill_list`. Built ahead of the rest in v0.3.0 (owner approved, see Wave C): the `job_stats` table records skills used per job and `agent-jobs stats --by skill` shows uses and success rate.
  - Delivery: copy only the selected skill directories (no symlinks, size cap, sha in job metadata) into the job's project `.claude/skills`; the report lists the skills used. Skills whose scripts reach the network or secrets are flagged; the guard and deny rules still apply; never the whole tree.
  - Native controls: `disable-model-invocation` for side-effect skills, `paths:` globs, `/skill-doctor` for context cost and never-invoked skills, `claude plugin eval` for trigger accuracy of 3-5 critical skills. Not adopted as a base: skills.sh, openskills, skillport (they widen distribution; the goal is narrowing); skillport's «metadata first» idea is borrowed.
  - Evidence, cited, to verify: arXiv 2604.04323 (from a market scan): with many weakly relevant skills the gain drops to near the no-skill baseline; skills refined to the task restore most of it (Terminal-Bench 2.0 57.7% → 65.5%).
  - Why: jobs get the right procedural knowledge without loading hundreds of skills. Source: owner request; market scan 2026-10-17. Related: Wave A `agent-jobs` skill and project cards. Priority: high. DEVIATIONS E7.

## v1.0.0: agent-jobs as a Claude Code plugin (planned)

Owner decision 2026-10-18 (see [DECISIONS.md](DECISIONS.md)): v0.4.0 ships as planned, with the items marked «built, released in 0.4.0» above. The next release after it is v1.0.0, which packages agent-jobs as a Claude Code plugin. The approach changes, so the major version goes up. *Status: plan only, nothing built.*

**Goal.** Anyone can install agent-jobs into their own Claude Code with one command (a plugin marketplace install). It arrives as an MCP server, hooks and a skill, and needs none of our private setup. It works in the plain terminal CLI and in the desktop app, without tmux. Inside a tmux session it gives the full mode we use today: job-done lines are pushed into the live session.

**Autonomous loop.** Job statuses, results and errors reach the orchestrator's context without being asked for:
Intended delivery path. Each item below is verified in P2 against the supported Claude Code versions and clients before it is relied on; none is a promise until then.
- Hook `additionalContext` on each prompt (`UserPromptSubmit`): a compact summary of the jobs that finished, failed or are waiting since the last turn. This is the floor.
- `asyncRewake`: a hook whose process exits with code 2 is meant to wake an idle session when a job ends. Async hooks are subject to timeouts, so the watcher lifecycle (start, restart, timeout, exit) must be verified.
- Plugin monitors (`experimental.monitors` in the plugin manifest, experimental) are an optional push channel in interactive sessions.
- tmux injection is kept only as the advanced mode.
- Desktop and sessions without tmux are meant to degrade gracefully: events are retained by the daemon, and the summary arrives with the next prompt. P2 acceptance below defines what is checked.

**Packaging.**
- A plugin manifest, with the bundled MCP server registered by the plugin.
- The hooks (context feed, rewake) and the `agent-jobs` skill.
- Daemon install and upgrade: a user service on Linux, launchd on macOS.
- A first-run doctor that checks the binary, the daemon, the store, the MCP registration and the hooks, and says what to fix.
- Config defaults that are safe for a stranger: the guard on, the API-credit fallback off, no private names, hosts or repos.

**Milestones.**
- **P1. Plugin skeleton + MCP + skill.** Manifest, MCP server registration, the `agent-jobs` skill. *Acceptance:* on a machine that already has the daemon, one install command makes the MCP job tools and the skill appear in a new Claude Code session, and `job_start` / `job_status` / `job_result` work end to end. Removing the plugin removes them.
- **P2. Context feed hooks + asyncRewake.** *Acceptance:* a job that finishes, fails or waits shows up in the next prompt's `additionalContext` once per job transition and receiving session (the same transition may reach another session once, and is never repeated to the same one), as a compact summary with a size cap. An idle session is woken by `asyncRewake` when a job ends, on the supported versions and clients that P2 lists. With the hooks off or failing, Claude Code still works and nothing is reported twice. Loss and replay are checked explicitly: (1) events that occur while the hooks are disabled or failing are retained and delivered after recovery, once; (2) when more events are pending than the summary cap allows, the overflow is not dropped: the summary says how many remain and they arrive in later prompts, once each; (3) a job that completes between a rewake and the next-prompt delivery is reported once, not twice and not zero times. Before the build, the behaviour is checked against the current Claude Code hook and plugin docs (`UserPromptSubmit`, `asyncRewake` and its timeout limits, `experimental.monitors`), and the supported versions, clients and watcher lifecycle are recorded.
- **P3. Daemon installer for Linux and macOS + doctor.** *Acceptance:* install, upgrade and uninstall are idempotent on Linux (user service) and macOS (launchd), and an upgrade never kills running jobs. `doctor` on a fresh install reports green; on a broken install (no daemon, stale binary, missing hook) it names the problem and the fix.
- **P4. Clean-machine acceptance.** On a fresh user account with only Claude Code installed, it is checked in three modes: the terminal CLI, the desktop app, and a tmux session. *Acceptance:* in each mode, one install command, a test job, its result in the orchestrator's context without manual polling (tmux: a pushed job-done line; terminal and desktop: the summary on the next prompt or a rewake). No private names in config, logs or prompts.
- **P5. Docs + release v1.0.0.** *Acceptance:* the README and the docs describe the plugin install as the primary path and the manual install as the alternative, with a migration note for v0.x. The CHANGELOG entry is written, the conformance check is published, and v1.0.0 is tagged after the owner's go.

**Open questions.**
- Windows support: not planned for v1.0.0 unless the owner decides otherwise. The daemon and the guard run on Linux today. Cgroup containment is Linux-only (a Linux kernel facility); containment and guard behaviour on macOS must be verified in P3 before macOS is claimed as supported.
- Channels (research preview, allowlist): not used as the default push path. They may be an opt-in later.
- Upgrades from an existing v0.x install (systemd unit, MCP entry in the user config, the skill installed by hand): how the plugin finds it, takes it over or leaves it alone, without two MCP servers or two daemons.

**Risks.**
- Hooks may behave differently in the terminal and in the desktop app (which events fire, whether `additionalContext` and rewake are honoured). P4 tests each mode, and the next-prompt summary is the floor.
- Monitors are experimental and work only in interactive sessions. They are never the only channel.
- `asyncRewake` hooks are subject to timeouts and may not wake a session in every client; the next-prompt summary stays the floor.

## Wave F: brief-acceptance gate

*Status: approved 2026-10-24; F1–F7, F9 and F10 built (not released), the rest not built.* Owner decisions of 2026-10-24 in [DECISIONS.md](DECISIONS.md); the items that diverge from the reference have a «proposed» entry in [DEVIATIONS.md](DEVIATIONS.md#proposed-wave-f). Takes ideas I1 (requirement ledger), I2 (blind acceptance job) and the REDPROOF and placeholder parts of I5 from «Ideas» below.

**Goal.** For large work, the owner's words become a numbered checklist that the owner approves once. Every job reports against that checklist, a blind judge checks the code at a given sha against the brief, and merge or deploy happens only at 100% acceptance. Nothing the owner asked for is lost or reinterpreted on the way. The gate is held by hooks and tools, not by the orchestrator's memory.

**Large vs small.** The orchestrator decides the size. LARGE = a new project, or a feature with more than 5 requirements, several jobs or more than a day of work; it goes through the brief flow below. SMALL (a fix, a single job) keeps the current pipeline. The owner can override («with brief» / «without brief»). A small task that grows is moved to the brief flow, and the owner is told.

**Owner flow.** The owner gives the brief by voice or text. Then come one or two short question rounds: no round has more than 4 questions, and each question already carries the answer we propose, so the owner can just agree. The owner approves the checklist once and at the end receives a single line «Acceptance: N of N» with a link or a screenshot.

**Files in the project repo.** Just two. `brief/BRIEF.md` keeps what the owner said, as said (with secrets masked, F2). Its text is frozen: whatever the owner adds later goes to the end of the file, under `## Additions`, as a dated quote. `brief/CHECKLIST.md` holds the numbered requirements. Job reports, verdicts and progress live in the agent-jobs store, never in the project repo. No dashboard for now.

**Merge rule.** A LARGE task is merged or deployed only at 100% acceptance on the approved checklist, or with an explicit owner waiver per requirement (F7: one waiver covers one requirement with any verdict other than `met`, at one checklist hash and one sha).

**Pack 1.**

- **F1. CHECKLIST.md format.** *Built (not released): `internal/checklist`.* A header (checklist id, brief file, version, and `approved: <time> owner sha256:<hex>`, written only by the tool) and a table `| ID | Brief quote | Contract | Rationale |`.
  - ID prefixes: `R` (from the brief), `Ri` (implied; the owner approves it), `G` (added later by the owner, also appended to the BRIEF `## Additions`), `D` (a constraint proven by a build; not counted in the 100%). Agent ideas (`A`) never enter the checklist; they live only in job reports, each with a parent `R`.
  - A **live requirement** is an `R`, `Ri` or `G` row with contract `live`. Only live requirements count in the 100%: `D` rows never do, `deferred` and `dropped` rows neither.
  - Contract: `live`, `deferred` or `dropped`, plus an optional `placeholder-ok`. `deferred` and `dropped` are the owner's decisions; the row's Rationale carries the owner's words.
  - Hash: sha256 over the normalized contract fields of every row (`ID|verbatim|contract|placeholder-ok|rationale`) plus the sha256 of `BRIEF.md`. Rationale is hashed because it records the owner's choices at forks and the reasons a row was deferred or dropped. Progress is not in the file and is not hashed; it is computed in the store.
  - Row size: each row is a single claim that a check can confirm or refute without looking at other rows. A long brief (1500+ characters) cut into fewer than 10 rows almost surely merges requirements; `checklist_set` warns.
- **F2. Checklist tools.** MCP tools `checklist_init`, `checklist_get`, `checklist_set`. `checklist_set` is the only writer of `version` and `approved`, and of owner waivers (F7); a manual edit of a hashed field (F1) voids the approval. It writes the BRIEF `## Additions` and the CHECKLIST in one operation. Secret redaction (Wave D) runs over BRIEF and CHECKLIST before writing and hashing: BRIEF is committed, so a secret must never reach the file; the hash is taken over the files as written, so the stored quote is the masked one. The tools are closed to the job role unless opened on purpose (allowlist rule). DEVIATIONS #28. *Built (not released): `internal/mcp/tools_checklist.go`, waivers in the store table `checklist_waivers`.*
- **F3. Slicing check before the owner approves.** *Built (not released): kind `slicing`, tools `slicing_start` / `slicing_get`, `checklist_set` `unmapped_decisions`; DEVIATIONS #30.* A separate read-only job sees BRIEF and CHECKLIST and nothing else, and sorts the gaps it finds into three lists. `unmapped`: passages of the brief that no `R` row points to. `half`: passages a row covers only in part. `invented`: rows with nothing in the brief behind them. Approval needs `unmapped` to be empty, or an owner decision on each of its entries.
- **F4. Requirements in job reports.** `job_start` takes `covers:[R..]`. Findings / Changes must contain a `### Requirements` block, one line per covered requirement: `R01 · done|partial|missing|placeholder|not-touched · evidence · ran: <cmd → result>`, plus a `REDPROOF` line for each new test (it failed before the code). A missing block = `report_off_contract`. `done` without `ran:` or without a REDPROOF counts as `claimed`, not done. Commit trailer `Requirements: R01, R03i`. DEVIATIONS #29. *Built (not released): `internal/jobs/requirements.go`; the trailer is read from the job's commits and shown in `job_result`, not enforced.*
- **F5. Kind `acceptance` (blind judge).** Working name; the final name must differ from `acceptance_cmd` (see Risks): built as kind `judge`. *Built (not released) with the manifest-check step: kind `judge`, tools `judge_start` / `judge_get`, records in the store table `gate_manifest_checks`; DEVIATIONS #31.* Read-only. Gets the full `BRIEF.md` (with Additions), the checklist rows (ID, brief quote, contract, rationale), the manifest-check output and the code at the sha; never job briefs, reports or diffs. A model family different from the coders is required for `release_check` (a codex judge for Claude coders); a same-family verdict is stored but cannot pass F7. DEVIATIONS F5.
  - Manifest-check step: before the judge starts, the wrapper of the `acceptance` job runs `scripts/manifest-check.sh` (F6) in a plain copy of the tree at the sha (no `.git`, no checkout filters or hooks; the script must be a regular file at that path), the way it runs `acceptance_cmd` (#18: the job's own containment, a scrubbed environment, no guard; not a boundary against a hostile script, see Risks), records its exit code and output tail in the store with the job, and passes the output to the judge; F7 reads that record. This is a new wrapper step, not #18 itself: `acceptance_cmd` runs after claude exits, only for fix and general jobs, and is refused for read-only kinds. Like #18 it is off unless config `acceptance_allowed` is true; without it the job fails before the judge starts, so nothing is recorded and `release_check` cannot pass.
  - Verdict: structured JSON written to the store by the wrapper, not by the orchestrator: `{checklist {id, sha256, version}, repo, sha, ran[], could_not_run, requirements[{id, verdict met|partial|missing|placeholder|cannot_check, how ran|read, evidence}], unmapped_brief[], extra_scope[], suspect_tests[]}`.
  - The wrapper validates it: every live requirement exactly once, the hash equals the approved one, the sha equals HEAD. An invalid verdict fails the job.
  - Judge rules. Nothing the judge does may reach beyond the machine; it halts at the last local step. It reports what it observed and gives no opinion on code quality. A verdict backed by a run outranks one backed by reading, since reading only tells what the code is meant to do. Code that exists but fails at its purpose gets `partial`. Brief passages that no requirement covers are listed.

**Risks.**

- The owner approves without reading. Mitigated by the slicing check (F3) and by approving diffs of changed rows only.
- 100% is unreachable for requirements that need accounts or external access. Owner waivers per requirement (F7).
- `[Rnn]` tags are formal: a tagged test may not test the requirement. REDPROOF and `suspect_tests`.
- A codex read-only judge cannot run the product. The `how` field (`ran` / `read`), and the acceptance wrapper runs manifest-check at the sha before the judge (F5).
- Name clash: `acceptance_cmd` vs kind `acceptance`. Pick distinct names before the build. Resolved: the kind is `judge` (pack 1b).
- Brief drift between BRIEF and CHECKLIST. The tool writes BRIEF Additions and CHECKLIST in one operation.
- The manifest-check script (F5 / F6) runs as the agent user without the guard or a sandbox: only environment variables are scrubbed. The wrapper reads the prompt before the script runs, fingerprints the rest of the judge's input and checks the approved brief files after it, which catches careless changes, not a determined one. So `release_check` holds against honest mistakes and careless coders, not against a hostile coder, until OS-level isolation of the script lands (hardening ticket 684). Accepted for now: the hook catches honest mistakes, it is not a boundary; branch protection in the target repo would close the rest and is not part of Wave F.
